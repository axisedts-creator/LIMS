Title: CR-C12-018: expose a metrics seam (gauge set) on the worker JobContext
From chunk: C12            To owner: C0-0D
Type: port
Blocking? no (C12.T-18 ships with the drift count in the log; the page rule InventoryBalanceDrift cannot fire until this lands)
Problem (what you cannot do today, with the user story / acceptance criterion it serves):
  02-TRD §9 says `inventory.balance_integrity_check` raises a "`balance_drift` alert + metric"; ops/inventory.rules.yml (TRD §13) rule InventoryBalanceDrift reads the gauge `lims_inventory_balance_drift_rows`. JobContext (services/worker/src/core, C0-0D) has no metrics handle, so job code cannot set a gauge and the page-severity rule never fires.
Proposed change (exact): TS signature diff in services/worker/src/core JobContext:
  + deps.metrics: { gauge(name: string, value: number, labels?: Record<string, string>): void }
  (implementation exports to the worker's existing Prometheus registry; tenant_id label set by core, not by job code)
Backward compatible? yes — additive field; existing jobs ignore it.
Tenant/security impact: no RLS change, no PHI; labels limited to tenant_id + names chosen by job code (no free text). REQ-SEC-024 unaffected.
IRD/regulatory impact (billing changes only): n/a
Alternatives considered: job writes its own registry (duplicates core, not owned path); log-based metric in ops (fragile, not the TRD §13 expression).
Tests that will prove it: C12 crons.integration test asserts deps.metrics.gauge('lims_inventory_balance_drift_rows', n) after a drift fixture; C0-0D unit test on the gauge export.
