Title: CR-C13-T14: worker retry of partners.issue_access_slip after a successful render re-mints a portal link and is refused by RenderPort
From chunk: C13            To owner: C6 (ReportingPort.issuePortalLink, RenderPort.renderPdf) / C0-0B (port contract)
Type: port
Blocking? no — C13 T14 ships; the gap is a rare retry path (render OK, then storage put or the final UPDATE fails).
Problem: services/worker/src/jobs/partners/tasks/partners.issue_access_slip.ts calls ReportingPort.issuePortalLink then RenderPort.renderPdf with idempotencyKey = access_slip_id (02-TRD §8.1, 08 A5.1). If the attempt fails after the render, the retry (10 attempts) mints a NEW link (new URL), so the render data differs and RenderPort rejects the same idempotencyKey with different data (common.idempotency_key_reused, packages/fakes). The slip then retries until it exhausts attempts and stays `requested`; the first link stays live but unused (US-09.3).
Proposed change (exact, owner to choose):
  A) issuePortalLink input gains optional `idempotencyKey: string`; same key + same reportId/versionNo returns the same link (same url, linkId, expiresAt) — C13 passes the access_slip_id; or
  B) RenderPort documents that a re-render under the same idempotencyKey with different data is allowed for the same templateKey (replace), or C13 may use key `<access_slip_id>:<attempt>`.
Backward compatible? yes (A: optional field; B: doc / key-format change only in C13).
Tenant/security impact: no RLS change; no new PHI; link URL still never persisted (ST12, 08 A2.1). A reduces live orphan links (smaller exposure).
Interim behaviour (until merged): retry after a post-render failure fails until attempts run out; the slip stays `requested` and the partner sees the PR-2 "taking longer" state; partner can request a new slip (new R4).
Alternatives considered: persist the URL to reuse it on retry (forbidden, ST12); revoke the first link on retry (no revoke API in ReportingPort today).
Tests that will prove it: worker access-slip test — first attempt fails at storage.put after render; retry issues the slip with one render-accepted call and (A) one distinct link.
