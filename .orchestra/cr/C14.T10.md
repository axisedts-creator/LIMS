Title: CR-C14-T10a: CatalogPort analyte-status lookup for library validation rule V13
From chunk: C14            To owner: C0-0C (implementing chunk C3 must agree)
Type: port
Blocking? no (C14.T10 ships with an empty `inactiveAnalyteIds` set, so V13 never fires; V13 is a warning only, 02-TRD §9.4)
Problem (what you cannot do today, with the user story / acceptance criterion it serves): 02-TRD §9.4 V13 — "analyte mappings whose catalog analyte is inactive" → warning `analyte_inactive` (validator V1–V14, AC-06.x). CatalogPortV1 (03-INTERFACE-CATALOG §4.2) has `getTest({requireActive})` for tests (used for V6) but no method that returns an analyte's active status. C14 may not read C3 tables directly (04-CHANGE-REQUESTS §1). So `library.service.ts` cannot find out which mapped analytes are inactive.
Proposed change (exact): additive method on CatalogPortV1:
  /** Active flag per analyte; unknown ids are omitted. ≤ 500 ids. @throws common.validation_failed */
  getAnalyteStatuses(ctx: RequestContext, input: { analyteIds: readonly Uuidv7[] }): Promise<ReadonlyArray<{ analyteId: Uuidv7; isActive: boolean }>>;
  (Name and limit are a proposal; C3's naming wins.)
Backward compatible? yes — additive port method; no existing caller changes. Fakes regenerated by C0.
Tenant/security impact: none new; read-only, tenant-scoped by ctx like every CatalogPort method; no PHI; no RLS change; no public surface.
IRD/regulatory impact (billing changes only): n/a
Alternatives considered: (1) reuse `referenceRangeFor`/`criticalLimitsFor` — they do not return status; (2) one `getTest` per test of the analyte — no analyte→test mapping on the port; (3) leave V13 off — current state, rule never fires.
Tests that will prove it: C14 `library.service.test.ts` — analyte mapping on an analyte the CatalogPort fake marks inactive yields warning `analyte_inactive` at `/mappings/<id>`; active analyte yields none; `valid` stays true (warning). Pure V13 already covered in `library.validate.test.ts`.
