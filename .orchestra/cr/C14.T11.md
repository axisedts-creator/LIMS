Title: CR-C14-T11a: render Problem.errors[] for smartreport.library_invalid (core toProblem)
From chunk: C14            To owner: C0-0D
Type: bug
Blocking? no (C14.T11 ships; service throws LimsError('smartreport.library_invalid', _, errors) with the issues, but they are dropped on the wire until core changes)
Problem (what you cannot do today, with the user story / acceptance criterion it serves): AC-06.5 / 03-APP-FLOW §2.1 step 4 — on submit of an invalid draft the client must see the V1–V14 issues. 08-CR-REGISTER:938 (= 03-INTERFACE-CATALOG:2738) defines `smartreport.library_invalid` (422) with meaning "Validation rules V1–V14 failed; details in errors[]". Core `services/api/src/core/errors.ts` `toProblem` (line 56) emits `errors[]` only when `code === 'common.validation_failed'` (02-CV §4.6:19 "errors[] only for validation"). So every `422 smartreport.library_invalid` (thrown at `modules/smartreport/library.service.ts:207` and `handlers/libraryChildren.ts:23`) reaches the client with no issues. Per precedence (CLAUDE.md), 08-CR-REGISTER outranks 02-CONVENTIONS; C14 does not own `src/core/`.
Proposed change (exact): in `toProblem`, replace
  if (code === 'common.validation_failed' && known?.errors?.length) {
with
  if ((code === 'common.validation_failed' || code === 'smartreport.library_invalid') && known?.errors?.length) {
(or, generally: any registry code whose `meaning` says "details in errors[]"; core's choice). Same clamping and sub-code whitelisting (SUB_CODES -> `common.field_invalid`) unchanged; C14 already sends `common.field_invalid` sub-codes with the V-rule code in `message`.
Backward compatible? yes — only adds `errors[]` to a response that today omits it; `_common.yaml#/Problem.errors` is already optional.
Tenant/security impact: none — no RLS change, no PHI (issues are JSON paths into the tenant's own library draft + rule codes); same 200-item/length clamps apply; no new public surface.
IRD/regulatory impact (billing changes only): n/a
Alternatives considered: (1) throw `common.validation_failed` instead — breaks the registry code AC-06.5 / smartreport.yaml name; (2) C14-local error hook — C14 may not edit core and would duplicate Problem rendering; (3) leave as is — AC-06.5 unmet on the wire.
Tests that will prove it: core `errors.test.ts` — `toProblem(new LimsError('smartreport.library_invalid', undefined, [{path:'/blocks/0', code:'common.field_invalid', message:'V3'}]), …)` has `errors[0].path === '/blocks/0'`; other non-validation codes still have no `errors`. C14 HTTP contract: POST submit on an invalid draft -> 422 body `errors.length > 0`.
