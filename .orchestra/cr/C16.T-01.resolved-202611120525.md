Title: CR-C16-024: register `x-extensible` as an annotation keyword in the HTTP ajv options (core/openapi.ts)
From chunk: C16            To owner: C0-0A (core services/api/src/core/openapi.ts)
Type: shared-lib
Blocking? yes — boot of the real modules directory. With modules/engagement/index.ts present, `src/__tests__/real-modules-boot.test.ts` ("bootstrap(...) resolves and serves core health") fails with `strict mode: unknown keyword: "x-extensible"`. C16-T01's own tests are green; the failure is outside C16's paths. Any later task that boots all modules (C16 T-02+ integration, partners C13) hits it.
Problem: contracts/openapi/engagement.yaml (T0C-10.C16, e.g. PatientReport.kind, 02-CV §7.2 / 08 A13 P-4) marks enums `x-extensible: true`. core/events/publish.ts:22 already registers that keyword for event schemas, but the HTTP ajv `keywords` list in core/openapi.ts:75 is `['x-coded-set', 'discriminator']`, so Fastify's strict-mode ajv rejects the spec when the engagement module is mounted. (partners.yaml uses it too.)
Proposed change (exact): core/openapi.ts:75  `keywords: ['x-coded-set', 'discriminator', 'x-extensible'],` — annotation only, no validation effect (an unknown enum value is still rejected by `enum`; the keyword only lets the spec load). Whether responses should tolerate unknown values is a separate decision, not requested here.
Backward compatible? yes
Tenant/security impact: none.
Alternatives considered: stripping `x-extensible` from engagement.yaml (rejected: contract change, 02-CV §7.2 requires the marker); module-local ajv (rejected: core owns the compiler).
Tests that will prove it: real-modules-boot.test.ts passes with modules/engagement present; a core openapi test that a spec with `x-extensible: true` loads.
