Title: CR-C2-T20: staff_web route rows for the tenant admin screens (nav manifest for AD-1..AD-15 + ME-1)
From chunk: C2            To owner: C0-0C (contracts/routes.yaml)
Type: api (route registry)
Blocking? yes — C2.T20 nav manifest (`features/admin/nav.manifest.ts`). `core/nav/build-nav.ts` rejects any routeId not in
contracts/routes.yaml and any parameterised route; routes.yaml has only `staff.admin.user` (/admin/users/{membership_id}) and
`staff.admin.audit_entry` (/admin/audit/{audit_id}), both parameterised, so not one admin nav entry can be built. Pages themselves are not blocked.
Problem: C2 04-UI-UX §1 lists the admin routes (group "Administration", one permission per page). Serves US-B1..B6, C1..C5, D1..D4, G1, A5/A6 (ME-1).
Proposed change (exact) — append to contracts/routes.yaml `routes:` (owner C2, origin staff_web):
  - { id: staff.admin.me,             origin: staff_web, path: "/admin/me",             owner: C2, permission: identity.self.manage }
  - { id: staff.admin.users,          origin: staff_web, path: "/admin/users",          owner: C2, permission: identity.user.read }
  - { id: staff.admin.user_new,       origin: staff_web, path: "/admin/users/new",      owner: C2, permission: identity.user.manage }
  - { id: staff.admin.roles,          origin: staff_web, path: "/admin/roles",          owner: C2, permission: identity.user.read }
  - { id: staff.admin.role_new,       origin: staff_web, path: "/admin/roles/new",      owner: C2, permission: identity.role.manage }
  - { id: staff.admin.role,           origin: staff_web, path: "/admin/roles/{role_id}", owner: C2, permission: identity.user.read }
  - { id: staff.admin.branches,       origin: staff_web, path: "/admin/branches",       owner: C2, permission: identity.user.read }
  - { id: staff.admin.centres,        origin: staff_web, path: "/admin/centres",        owner: C2, permission: identity.centre.read }
  - { id: staff.admin.settings,       origin: staff_web, path: "/admin/settings",       owner: C2, permission: identity.settings.manage }
  - { id: staff.admin.sessions,       origin: staff_web, path: "/admin/sessions",       owner: C2, permission: identity.session.revoke }
  - { id: staff.admin.audit,          origin: staff_web, path: "/admin/audit",          owner: C2, permission: audit.log.read }
  - { id: staff.admin.access_log,     origin: staff_web, path: "/admin/access-log",     owner: C2, permission: audit.log.read }
  - { id: staff.admin.exports,        origin: staff_web, path: "/admin/exports",        owner: C2, permission: audit.log.export }
  - { id: staff.admin.support_access, origin: staff_web, path: "/admin/support-access", owner: C2, permission: audit.log.read }
  - { id: staff.admin.access_review,  origin: staff_web, path: "/admin/access-review",  owner: C2, permission: identity.user.read }
  The manifest C2 will then add (group admin, ids admin.*, order ascending): me, users, user_new, roles, branches, centres, settings,
  sessions, audit, access_log, exports, support_access, access_review (13 entries; no chords — §3 keeps `n`/`/` page-local).
Backward compatible? yes — additive rows.
Tenant/security impact: none (route registry only; each page still checks its permission server-side before any API call, REQ-SEC-080).
Alternatives considered: reusing the two parameterised ids (rejected: build-nav refuses parameterised nav routes); putting ME-1 in the
shell user menu instead of the manifest (possible, but AppShell is C0-owned — same CR cost).
Interim behaviour in code: all pages, help files and loading/error boundaries ship; `features/admin/nav.manifest.ts` is NOT created
(build:nav would fail and break every lane's nav build). The 2 manifest tests in t20.static.test.ts stay red until this CR lands.
Tests that will prove it: `pnpm --dir apps/web run build:nav` passes with the manifest; t20.static "nav manifest" + "My account reachable".
