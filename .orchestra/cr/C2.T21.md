Title: CR-C2-T21: PlatformRequestContext gains `aal` and `platformSessionId`
From chunk: C2            To owner: C0-0D
Type: port
Blocking? no for T21 tests (fake ctx supplies both); yes for live platform support endpoints (C2.T21 openSupportSession/activateSupportSession/endSupportSession/listPlatformSupportSessions).
Problem: CR-C2-004 (C2 02-TRD:737) fixes `PlatformRequestContext { actor, requestId, tx, now, platformRole, platformStaffId }`. The codes T21 checks (platform.support_session.open, platform.tenant.read) are `privileged: true` (contracts/permissions.yaml:46,48), so PlatformAuthz needs the caller's `aal` (REQ-SEC-067) or it must throw auth.mfa_required on every call. SP1/SP6/SP8 (03-APP-FLOW §2.4) bind a support session to the caller's platform session (support_sessions.platform_session_id), which needs the platform `lims_session_id`. Neither is on the core context. Serves AC-E4.1–E4.6.
Proposed change (exact): `PlatformRequestContext` adds `readonly aal: 'aal1' | 'aal2'` (from platform claims `aal`, 02-TRD:349) and `readonly platformSessionId: string` (from platform claims `lims_session_id`, 02-TRD:349). Both populated by the claims resolver when scope = 'platform'.
Backward compatible? yes (additive fields on the context; no existing consumer reads them).
Tenant/security impact: no RLS change; no PHI; no new public surface. Enables the aal2 gate on privileged platform codes (REQ-SEC-067) instead of failing closed for all callers.
Alternatives considered: re-reading aal / session id from the DB in C2 (rejected: duplicates resolver work, extra query per call); dropping the aal2 check (rejected: REQ-SEC-067).
Tests that will prove it: resolver test — platform claims with aal='aal2', lims_session_id=X yield ctx.aal='aal2', ctx.platformSessionId=X; support.integration.test.ts runs against the real core context without auth.mfa_required / auth.unauthenticated.
