Title: CR-C2-T22-detail: platform read path for getTenant counts / status history / annex readiness
From chunk: C2            To owner: C2 (05-SCHEMA §10.2) / C0 (05-SCHEMA §10 DEFINER inventory, 08 A12.3)
Type: schema
Blocking? no for T22 tests (fake repo); yes for a correct live getTenant (R10.x detail): without it the detail shows users/branches/centres = 0, status_history = [] and annex_readiness = 'incomplete'.
Problem: getTenant runs under platform claims outside withTenantScope (correctly not on the D-214 list). Its detail query (services/api/src/modules/identity/service/tenant.service.ts repo.detail) reads core.memberships, core.branches, core.collection_centres, identity.ird_annex_records and audit.audit_log. None of these has a `__platform` SELECT policy (C2 05-SCHEMA §10.2 has platform policies only on core.tenants, identity.tenant_settings, identity.sessions). With RLS FORCE every subquery returns nothing. Serves AC-E1.1/AC-E1.2 (operator sees tenant readiness before activation).
Proposed change (exact): a SECURITY DEFINER `app.platform_tenant_detail(p_tenant_id uuid) RETURNS TABLE (users integer, branches integer, centres integer, annexes_done integer, history jsonb)` owned by `lims_owner`, EXECUTE to `lims_api` (platform context only), modelled on `app.platform_list_tenants` (08 A12.3): sets `app.maintenance = 'platform_tenant_detail'`, checks platform claims, returns only non-PHI aggregates (counts; status from/to/at from audit rows of core.tenants, newest 200), resets the GUC before returning; owner policies `TO lims_owner` on the five tables matching that GUC. repo.detail then calls this function instead of the raw SELECT.
Backward compatible? yes (additive function + owner-only policies).
Tenant/security impact: no new PHI exposure (counts and status transitions only); no broad __platform SELECT policy on tenant tables; A12.7-style tests for GUC reset and claims check.
Alternatives considered: `__platform` SELECT policies on the five tables (rejected: exposes full membership/audit rows to platform context); running detail inside withTenantScope (rejected: D-214 limits withTenantScope for platform reads to the R10.4 list).
Tests that will prove it: DB test under platform claims returns real counts/history for a seeded tenant; non-platform caller rejected; `app.maintenance` is '' after the call.
