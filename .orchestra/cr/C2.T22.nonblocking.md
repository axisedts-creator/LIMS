Title: CR-C2-T22: LD-29 contract-acceptance table + provisionTenant wire for LD-26 training_mode / LD-29 contract_acceptance
From chunk: C2            To owner: C2 (05-SCHEMA / identity migrations, contracts/openapi/identity.yaml TenantProvisionRequest, TenantSettingsDto)
Type: schema + contract
Blocking? no for T22 tests (fake repo); yes for a real provisionTenant: the default SQL repo writes identity.tenant_contract_acceptances (missing) and tenant_settings.training_mode (CR-C2-T16, missing), so every live provisioning fails loudly until both land.
Problem: LD-29 requires append-only acceptance rows (tenant_id, document 'tos'|'dpa', version text <= 32, accepted_by_name, accepted_by_title, accepted_at, recorded_by) in C2's schema with RLS per the 02 template, readable by platform operators and the tenant admin; no table exists and no name is given. TenantProvisionRequest (additionalProperties:false) has neither `training_mode` (LD-26) nor `contract_acceptance` (LD-29), so the core schema guard would reject both today. TenantSettingsDto has no `training_mode`.
Proposed change (exact): (1) `CREATE TABLE identity.tenant_contract_acceptances (id uuid PK, tenant_id uuid NOT NULL FK core.tenants, document text NOT NULL CHECK (document IN ('tos','dpa')), version text NOT NULL CHECK (char_length(version) BETWEEN 1 AND 32), accepted_by_name text NOT NULL CHECK (char_length BETWEEN 1 AND 120), accepted_by_title text NOT NULL CHECK (char_length BETWEEN 1 AND 80), accepted_at timestamptz NOT NULL, recorded_by uuid NOT NULL, created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL)`; INSERT/SELECT __tenant policies + SELECT __platform policy; no UPDATE/DELETE grant (append-only); audited. `recorded_by` = the platform staff user id (platform staff hold no membership). (2) TenantProvisionRequest: `training_mode: boolean` (default false); `contract_acceptance: {tos: Acc, dpa: Acc}` required, Acc = {version (1-32), accepted_by_name (1-120), accepted_by_title (1-80), accepted_at IsoUtc}, all required, additionalProperties false. (3) TenantSettingsDto: read-only `training_mode: boolean`; not in TenantSettingsPatch.
Backward compatible? schema additive; the request becomes stricter (contract_acceptance required) by LD-29's own rule.
Tenant/security impact: new tenant-scoped table under the standard RLS template; rows written only inside withTenantScope(new tenant) by provisionTenant.
Alternatives considered: storing acceptances in tenant_settings columns (rejected: LD-29 says append-only rows, re-acceptance of new versions must keep history).
Tests that will prove it: migration test insert/select under tenant + platform claims, UPDATE/DELETE denied; tenant.service tests already cover the wire (both required, version <= 32).
