Title: CR-C2-T27: platform scope for `identity.import_breached_passwords` + access-review notice for a tenant with no review
From chunk: C2            To owner: C0-0D (worker core: manifest/tasklist); C0-0B (`admin_notices__subject__ck`, 05-SCHEMA); C2 doc owner (02-TRD §10)
Type: port (1); schema (2)
Blocking? (1) yes — `identity.import_breached_passwords` (C2.T27) can never run. (2) no — current behaviour kept until ruled.
Problem (what you cannot do today, with the user story / acceptance criterion it serves):
(1) 02-TRD §10 line 538: `identity.import_breached_passwords` is "manual (platform CLI)", payload `{}`, idempotent by file sha256,
    max_attempts 3. It has no crontab entry, so `services/worker/src/core/tasklist.ts:60` registers it `per_tenant` ([CONV] default).
    Core then refuses the `{}` payload (no `tenant_id`); with a `tenant_id` the handler's `platformOnly` guard
    (`services/worker/src/jobs/identity/tasks/import_breached_passwords.ts`) rejects it. The breached-password list (05-SCHEMA §6, §10.3)
    can therefore never be loaded. Same gap as CR-C2-T11 item (1).
(2) 02-TRD §10 line 552 / US-G1 / REQ-SEC-140 (quarterly review): `identity.access_review_due` inserts a notice with subject `access_review`
    = the last review. A tenant that has NEVER recorded an access review has no subject id, and `admin_notices__subject__ck`
    (05-SCHEMA line 352/1182) allows NULL `subject_id` only for kind `login_ip_throttled`. Such a tenant gets no `access_review_due`
    notice (`services/worker/src/jobs/identity/tasks/access_review_due.ts:42`), although its review is the most overdue.
Proposed change (exact):
(1) Reuse CR-C2-T11's proposed manifest field: task entry `scope: 'platform'` for `identity.import_breached_passwords`
    (core runs the handler with ctx.tenantId = undefined under system claims, skips `tenantOf`, accepts payload `{}`).
    No new DEFINER: the task already calls `app.identity_load_breached_batch(p_hashes, p_version)` / `app.identity_finish_breached_import(p_version)`.
(2) Decision needed, one of:
    (a) `admin_notices__subject__ck`: allow `subject_id` NULL also for kind `access_review_due` (subject_type `access_review`,
        NULL = "no review yet"); due when no review exists and the tenant was activated > 90 days ago (or immediately — to be ruled).
    (b) keep the ck; for a tenant with no review, count 90 days from the tenant activation date and use a different subject
        (would need a new subject_type, e.g. tenant — needs its own ck change).
    (c) keep current behaviour (no notice until the first review); the US-G1 banner in the UI covers "never reviewed".
    C2 recommends (a) (additive, mirrors the `login_ip_throttled` NULL case).
Backward compatible? yes — (1) `scope` defaults to 'tenant'; (2a) relaxes a CHECK only.
Tenant/security impact: (1) no RLS change; task touches only the platform breached-hash table through existing owner-role DEFINERs.
(2a) no RLS change, no PHI; notice row still tenant-scoped under `withTenantScope`.
IRD/regulatory impact: none.
Alternatives considered: (1) give the task a crontab entry with `tenantScope: 'platform'` (rejected: 02-TRD says manual, not scheduled);
enqueue with a sentinel tenant_id (rejected: platformOnly guard and platform rows have NULL tenant).
Tests that will prove it: (1) worker core test: platform-scope non-cron task accepts payload `{}`, runs with tenantId undefined;
C2.T27 integration: import job enqueued via core reaches the DEFINERs. (2a) pgTAP s11 test 28 extended: NULL subject_id accepted for
`access_review_due`; vitest: tenant with no review and age > 90 d gets exactly one notice.
