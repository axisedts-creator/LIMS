Blocking? no (T-25 ships with the behaviour below; only the contract declaration is missing)
Problem (what you cannot do today, with the user story / acceptance criterion it serves):
1. AC-19.4 / S-16: releasing an already-released hold must be refused (one release wins). The implementation returns 409 `common.version_conflict`, but contracts/openapi/lab.yaml `releaseQcHold` declares no 409 response and no `common.version_conflict` in `x-error-codes` (02-CONVENTIONS: every returnable code must be declared). 02-TRD §5.7 row 46 is silent too.
2. `lab.qc_holds` has no centre (tenant-wide) but the `on_hold = false` UPDATE on `lab.results` runs under centre RLS (`results__update__tenant_centre`). A centre-scoped lab_manager would mark the hold released while only freeing results in their own centres; other centres' results stay on_hold with a released hold_id and can never be released. Spec is silent on release scope.
Proposed change (exact):
- lab.yaml `releaseQcHold`: add `'409': $ref: '#/components/responses/Conflict'` (or the module's equivalent problem response) and add `common.version_conflict` to `x-error-codes`. 02-TRD §5.7 row 46: add "409 common.version_conflict (hold not active)".
- 02-TRD §5.7 row 46 / 07-SECURITY S-16: add "actor must hold all-centres scope; centre-scoped actor -> 403 auth.forbidden" (`auth.forbidden` is already declared).
Backward compatible? yes — additive response code; the scope rule narrows who may call (no consumer yet).
Tenant/security impact: no RLS change; tightens authorisation (REQ-SEC-017 centre scope). No PHI.
Alternatives considered: (a) add centre_id to qc_holds and release per centre — schema change, larger; (b) run the results UPDATE without centre RLS — breaks centre isolation. Rejected.
Tests that will prove it: services/api/src/modules/lab/handlers/__tests__/qc.handlers.integration.test.ts — "review T-25 #2" (scoped actor -> 403, hold active, results on_hold) and the existing already-released -> 409 case.
