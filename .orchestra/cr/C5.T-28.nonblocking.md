Title: CR-C5-T28-001: CatalogPort read for the tenant's current catalog revision
From chunk: C5            To owner: C3
Type: port
Blocking? no (T-28 ships an interim read; see Alternatives)
Problem: 02-TRD §6.2 (CatalogPort row) keys the C5 in-process cache by (tenant, method, input, catalogRevision). The API process never receives the worker's catalog.changed.v1 invalidation (T-28 review item 1), so the wrapper must read the tenant's current revision before each lookup. CatalogPort exposes no such read; only resolveOrderables returns catalogRevision. 01-CHUNK-MAP R1 forbids C5 from importing catalog code or reading catalog tables.
Proposed change (exact): add to CatalogPort: `currentCatalogRevision(ctx: RequestContext): Promise<number>` — the tenant's catalog.catalog_state.catalog_revision, 0 before the first write, runs in ctx.tx (C3 already has `currentRevision(tx, tenantId)` in modules/catalog/repo/catalogState.repo.ts).
Backward compatible? yes (additive method).
Tenant/security impact: none; RLS-scoped read in the caller's transaction, tenant from ctx only (REQ-SEC-024). No PHI.
Alternatives considered: interim (in T-28): services/api/src/modules/lab/service/cache.ts `currentRevision` runs `SELECT catalog_revision FROM catalog.catalog_state WHERE tenant_id = $1` in ctx.tx — an R1 deviation, marked [CONV]; replaced by the port method once added (one-line change of the default `readRevision`).
Tests that will prove it: C3 CatalogPort contract test (revision 0 before first write, N after N writes, tenant-isolated); C5 cache.test.ts already injects `readRevision`.
