Title: CR-C5-T29-001: LabCodeDto needs `version` so a tenant code row can be edited again (#54 If-Match)
From chunk: C5            To owner: C0-0C
Type: api
Blocking? no (T-29 ships #53/#54; /lab/settings offers Edit only on GLOBAL rows (override = PUT without If-Match) until this lands)
Problem: 02-TRD §5.8 #54 upsertLabCode (contracts/openapi/lab.yaml, operationId upsertLabCode) requires If-Match once a tenant row exists
  (errors common.precondition_required / common.version_conflict). The list #53 returns LabCodeDto (lab.yaml:7512, additionalProperties false)
  with code/display/sort_order/is_active/source but no `version`, so a client cannot build If-Match for a TENANT row. Result: after its first save
  a tenant code cannot be edited from /lab/settings (04-UI-UX §3.13 reason codes tab; AC-12.4 configuration story).
Proposed change (exact): LabCodeDto gains optional `version` (integer, minimum 1), present when source = tenant, absent for global rows.
  Handler #53 fills it from the tenant table's `version` column of that coded set (tenant rows). Client sends If-Match: "<version>" on #54 for tenant rows.
Backward compatible? yes (optional response field).
Tenant/security impact: none (no PHI; version is a row counter); same RLS, permission lab.config.manage unchanged.
Alternatives considered: per-entry ETag on #53 (list responses carry no per-item headers); a GET-one endpoint for a code (extra route + round trip).
Tests that will prove it: config.handlers.integration (#53 tenant rows carry version; #54 with that If-Match -> 200, stale -> 409 common.version_conflict)
  and the /lab/settings ReasonCodesTab component test (Edit offered on tenant rows, sends If-Match).
