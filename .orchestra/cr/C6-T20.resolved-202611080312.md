Title: CR-C6-021: core credential pre-checks must not pre-empt the portalSession `reporting.link_invalid` answer
From chunk: C6            To owner: C0-0D
Type: api
Blocking? yes — C6-T20 (06-IMPLEMENTATION-PLAN row C6-T20; done_when "identical invalid responses"), test portal.resolver.test.ts "every invalid credential rejects reporting.link_invalid…" case 'too long'.
Problem (what you cannot do today, with the user story / acceptance criterion it serves):
  spec/chunks/C6-reporting-delivery/01-PRD.md:218 AC-11.5 requires an identical `404 reporting.link_invalid` for expired, revoked, unknown OR MALFORMED link tokens; 07-SECURITY.md:38 REQ-SEC-095 requires identical `link_invalid` bodies.
  services/api/src/core/auth/resolvers.ts:36 (C0-owned) throws `auth.unauthenticated` (401, 03-INTERFACE-CATALOG.md:2459) for any credential that is empty or > MAX_CREDENTIAL (4096, a [CONV] not in the spec) BEFORE the module resolver runs.
  So `link.` + 5000 chars answers 401 auth.unauthenticated instead of 404 reporting.link_invalid; C6 cannot fix this inside its own paths. 08-CR-REGISTER.md:463 (CR-C6-001) and :1398 define only that the resolver "may return { error: 'reporting.link_invalid' } → 404"; the core pre-check behaviour is unspecified.
Proposed change (exact):
  03-INTERFACE-CATALOG / C0 TRD §6 (authResolvers): "A resolver key may declare `invalidError: ErrorCode` (portalSession: 'reporting.link_invalid'). Core's pre-resolver rejections (empty, non-string, over-length credential) for that key throw that error instead of auth.unauthenticated." Keep the 4096 cap (DoS bound) — only the error code changes.
  TS: `authResolvers.portalSession?: AuthResolver & { invalidError?: ErrorCode }` (or a registry option keyed by resolver name).
Backward compatible? yes — other resolver keys keep auth.unauthenticated.
Tenant/security impact: no RLS change, no PHI, no new public surface. Strengthens REQ-SEC-095 (no length oracle on the public portal surface); cap still bounds input (REQ-SEC-019..021 unchanged).
IRD/regulatory impact: none.
Alternatives considered: (a) shorten the test token below 4096 — leaves AC-11.5 "malformed" violated for long tokens; (b) map 401→404 in C6 handlers — handlers never run when auth fails in core; (c) remove the cap — DoS risk, rejected.
Tests that will prove it: core resolvers test: portalSession with 5000-char / empty credential → reporting.link_invalid, other keys → auth.unauthenticated; C6 portal.resolver.test.ts 'too long' case passes unchanged.
