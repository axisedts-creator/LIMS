Title: CR-C6-0xx: test-support endpoints for the C6-T34 nightly E2E journey and load seed (non-production only)
From chunk: C6            To owner: C0-0C (contracts) / C0-0D (compose, nightly)
Type: api
Blocking? no — C6-T34 harness is written against the proposal below; the real nightly/load run is blocked until these exist in the compose/ci stack.
Problem (what you cannot do today, with the user story / acceptance criterion it serves):
  C6-T34 (05-DoD §5.2 journey; 02-TRD §11 load at 10x seed) must register an order, approve results, record a payment, run the rejection/recollection and cancel/credit-note flows, read what the recording WhatsApp/SMS provider "sent" (portal credential, OTP code), read the QR token of a version, scan logs for PHI, and seed 10x synthetic reports. 03-IC lists no C3/C4/C5 HTTP routes for register/approve/pay, and no spec defines a seed or recording-provider read surface. The harness must not invent routes (CLAUDE.md), so they are proposed here.
Proposed change (exact): mounted ONLY when TARGET_ENV/APP_ENV ∈ {compose, ci, staging}; absent (404) in production; staff auth + tenant RLS like every /v1/reporting route; synthetic data only.
  POST /v1/reporting/test-support/scenarios        {scenario: journey|rejection-recollect|cancel-credit-note|narrative|outsourced, dues?: outstanding|none}
       -> 201 {order_id, order_item_ids[], patient_display_name, phone, released_report_count?, credit_note_id?}   (registers via the owning chunks' ports)
  POST /v1/reporting/test-support/scenarios/{order_id}/approve    {}  -> 200 {}   (approves all lab results of the order via LabPort test hook)
  POST /v1/reporting/test-support/scenarios/{order_id}/payments   {}  -> 200 {}   (records full payment via BillingPort test hook)
  GET  /v1/reporting/test-support/recorded-messages?order_id=&kind=whatsapp|sms|otp&purpose=report|dues
       -> 200 {data: [{kind, channel, purpose, body, portal_credential?, otp_code?}]}
  GET  /v1/reporting/test-support/report-versions/{report_version_id}/qr-token  -> 200 {qr_token}
  GET  /v1/reporting/test-support/logs?order_id=   -> 200 text/plain (api + worker log lines for the order's request ids)
  POST /v1/reporting/test-support/seed  {count >= 200 (E2E bulk release uses 200; the k6 load run itself refuses < 10000)}
       -> 201 {report_ids[] (ready, unreleased), report_version_ids[] (rendered, unreleased), released_report_ids[], qr_tokens[]}
Backward compatible? yes — additive, non-production only.
Tenant/security impact: new surface that exposes raw OTP codes, portal credentials and QR tokens — must never be mounted in production (startup assertion + CI check that the production OpenAPI has no /test-support path). No real PHI (synthetic only).
Alternatives considered: (a) Playwright through the UIs of C3/C4/C5 — still needs a recording-provider read surface and is slower; (b) direct DB fixtures from the test runner — bypasses RLS and the ports the journey is meant to prove.
Tests that will prove it: `node --test tests/load/C6-T34.static.test.mjs` (harness contract); nightly `npx vitest run tests/e2e/reporting-journey.e2e.ts` and `k6 run tests/load/reporting-load.js` green against compose.
