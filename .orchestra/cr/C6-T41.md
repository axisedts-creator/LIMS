Title: CR-C6-028: durable pending regeneration reason on `reporting.reports` (R9 reason lost on keyed-job collapse)
From chunk: C6            To owner: C0-0B
Type: schema
Blocking? yes — C6-T41 (R9 regenerateReport; AC-02.6, AC-06.9, E8, 02-TRD §10 row (f)/(l) D-33)

Problem:
02-TRD §6.3 R9 says "store `reason_code`/`reason_text` for the next version (`report_versions.regeneration_reason_code/_text`)"; §4.5 rule 0 makes that version `amended` with a "Report details" note.
`reporting.reports` (05-SCHEMA line 66 area) has no column to hold the reason until the next version exists, so today it travels only in the
payload of the keyed job `assemble:<report_id>` (02-TRD §9, producers: consumers, narrative sign, outsourced confirm, regeneration, sweep).
`app.enqueue_job` (db/migrations/20261105001200_app__create_queue_wrapper.sql:30) calls `add_job` with `job_key_mode => 'unsafe_dedupe'`:
if any `assemble:<id>` job already exists (queued or running), the R9 enqueue is silently dropped. (The C6-T41 review said `replace`; the
mode is actually `unsafe_dedupe`. The outcome is the same — R9's payload loses to the other producer.) The counter is already bumped and `needs_assembly`
set, so a version is still built, but without the reason: after a release it is NOT `amended`, has no "Report details" note, and
`report_versions.regeneration_reason_code/_text` stay NULL. AC-02.6 fails whenever a consumer/sweep job is pending.

Proposed change (exact, additive), preferred option (a):
  ALTER TABLE reporting.reports
    ADD COLUMN pending_regeneration_reason_code text NULL,
    ADD COLUMN pending_regeneration_reason_text text NULL,
    ADD CONSTRAINT reports__pending_regen__ck CHECK (
      (pending_regeneration_reason_text IS NULL OR char_length(pending_regeneration_reason_text) <= 500)
      AND (pending_regeneration_reason_code IS NOT NULL OR pending_regeneration_reason_text IS NULL));
  + add both columns to the reports__mutable_columns trigger allow-list (05-SCHEMA line 556).
  Semantics: R9 sets them (under the report lock, last R9 wins); `reporting.assemble_report` reads them under its report-row lock, copies them to
  the new `report_versions.regeneration_reason_code/_text`, and clears them in the same tx (like `needs_assembly`). If no new version is built (fingerprint unchanged), they stay set for the next one.
  The job payload `regeneration` field is then dropped.
Option (b), no DDL: every producer of `assemble:<id>` merges `regeneration` into an existing job instead of dropping or replacing it. Rejected: needs
a change in app.enqueue_job (C0) plus every producer, and still loses the reason if the job is already locked/running.

Backward compatible? yes (nullable columns; no consumer reads them outside C6).
Tenant/security impact: no RLS change (same row, existing tenant policy). reason_text is free text (P2), same class as
report_versions.regeneration_reason_text; never logged or echoed (07-SECURITY). No new public surface.
IRD/regulatory impact: none.
Alternatives considered: (b) above; a separate `reporting.pending_regenerations` table (more objects, same effect).
Tests that will prove it: assemble_regeneration.test.ts "KNOWN GAP" block flips: an R9 followed by a consumer enqueue (payload without
`regeneration`) after a release gives v2 `amended` + one "Report details" note + stored reason; columns NULL after assembly; R9 twice
before assembly -> last reason stored; unchanged fingerprint -> pending reason kept. Real-PG test: mutable-columns trigger allows the two columns.
