Title: CR-C9-0xx: TAT alert DTO `department_id` for an item without a department; staff-name lookup for `acknowledged_by_display`
From chunk: C9            To owner: C9 spec (TRD §5.10 / quality.yaml TatAlertDto) and C0-0B (identity) — owner to confirm
Type: contract (1) + port (2)
Blocking? no (T-19 omits `department_id` for such an item and reads the staff name from core.memberships + core.users; both are reversible)
Problem: (1) quality.yaml TatAlertDto / TatAlertDetailDto list `department_id` as required and non-nullable, but quality.tat_items.department_id is nullable (05-SCHEMA, lab.v_pub_pending_items.department_id may be absent).
  An item without a department cannot satisfy the schema. (2) `acknowledged_by_display` needs a staff label; the spec names no directory view (same gap as C9.T-15.nonblocking.md). 03-IC §6 says core tables are read
  through C0's `ctx.core` repository, which the tat repo test seam (tat.repo.sql.test.ts listMembershipLabels) models as one tenant-scoped statement; T-19 reads core.memberships JOIN core.users (display_name only).
Proposed change (exact): (1) make `department_id` optional in TatAlertDto / TatAlertDetailDto (remove it from `required`), or define the value for a department-less item. (2) confirm reading core.memberships/core.users display_name
  for labels, or add `identity.v_pub_user_directory` / `IdentityPort.getUserLabels` (see C9.T-15.nonblocking.md) and switch TatRepo.listMembershipLabels to it.
Backward compatible? yes (additive / relaxing a `required`).
Tenant/security impact: display names only, tenant-scoped; no new PHI. The raw membership id never leaves the API (REQ-SEC-081).
Alternatives considered: emit null (rejected: schema is non-nullable); fabricate a placeholder uuid (rejected: invents data); drop the alert (rejected: hides a real breach).
Tests that will prove it: tat.service.test.ts DTO test (item with department_id null: key absent, no undefined values); tat.repo.sql.test.ts listMembershipLabels (tenant predicate).
