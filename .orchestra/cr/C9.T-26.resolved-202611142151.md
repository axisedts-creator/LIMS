Title: CR-C9-T26-002: carry `metrics` on the worker JobContext and the API HandlerContext so module emissions reach /metrics
From chunk: C9            To owner: C0-0D (services/worker/src/core/consumer.ts, services/worker/src/core/manifest.ts, services/api/src/core/pipeline/index.ts)
Type: shared-lib
Blocking? yes. C9 T-26 done_when ("metrics in 02-TRD 14 exported") is unmet. Test services/worker/src/jobs/quality/__tests__/sync_qc_observations.metrics.test.ts fails today because jobContext drops deps.metrics. Review item 1 is in .orchestra/notes/C9.T-26-review.md.
Problem: Every C9 emit is `ctx.metrics?.…` (observation.service, run.service, QualityPort.impl, worker tasks close_stale_runs and tat_sweep). Neither runtime context has a `metrics` field, so in production none of the 16 lims_quality_* series is exported. All 7 quality.rules.yml alerts therefore evaluate on absent series, and QualityQcSyncStalled can never fire. Analytics (refresh.service.ts:96) uses the same `ctx.metrics?.` pattern, so it has the same gap.
Proposed change (exact):
  services/worker/src/core/manifest.ts, interface JobContext: add
    readonly metrics: WorkerDeps['metrics'];   // inc/set/observe, same shape as tasklist.ts:18
  services/worker/src/core/consumer.ts jobContext() (line ~59): add `metrics: deps.metrics,` to the ctx literal.
  services/api/src/core/pipeline/index.ts HandlerContext literal (~line 132), plus the HandlerContext type: add
    metrics: d.metrics   // CoreMetrics { inc, set, observe }, the same object boot.ts passes as o.metrics. Do not use PortMetrics, which exposes setGauge rather than set.
  The ports ctx that reaches QualityPort.impl should carry the same CoreMetrics, so that lims_quality_port_duration_seconds is emitted.
Backward compatible? yes. The change only adds fields, and existing handlers ignore them.
Tenant/security impact: none. No RLS or PHI change and no new public surface. Label values are still validated by createMetrics DEFS (REQ-SEC-098).
Alternatives considered: (a) Capture metrics in quality createServices({env,log,metrics}). This covers API services only. It does not cover worker tasks, and the tester's test requires metrics to come from jobContext. (b) Have each module import a global registry. This bypasses DI and breaks the fakes.
Tests that will prove it: services/worker/src/jobs/quality/__tests__/sync_qc_observations.metrics.test.ts (real createMetrics through taskRun asserts lims_quality_qc_sync_last_success_timestamp_seconds{tenant_id}). Existing core consumer/pipeline tests must still pass.
