## Items

### 1. The payments module is wired to placeholder handlers: every payments operation answers 503  (To: payments owner) (verified, 5 screens)
Problem: `services/api/src/modules/payments/handlers/index.ts:6` `notYet` is the PG-T01 placeholder that always throws `common.service_unavailable`; `payments/index.ts:6,20` registers only `handlers/index.js`. The real handler factories exist in the same folder (`handlers/intents.ts:80` `createIntentHandlers(deps)` with `listPaymentIntents` at :114, `service/refund.service.ts:70`, reconciliation, static QR, merchant and settings factories) but are never imported. Screens: /payments/review (`listPaymentIntents` 503), /payments/refunds (`listPaymentRefunds`), /payments/reconciliation (`listReconciliationRuns`, `listReconciliationFindings`), /payments/static-qr (`listStaticQrReconciliations`, `previewStaticQrReconciliation`), /payments/settings (`getPaymentSettings`).
Also: /payments/settings fails in the web before any api call: `Error: LIMS_PAYMENTS_GATEWAY_ENV must be "uat" or "production"` (`apps/web/src/app/(staff)/payments/settings/page.tsx:14-15`); the web container has no such variable.
Proposed change: wire the real factories with their dependencies in `payments/index.ts` (the `implemented` list), keep the placeholder only for operations without an implementation; set `LIMS_PAYMENTS_GATEWAY_ENV` (value `uat` or `production`, deploy decision: this tenant is a demo, so `uat`) in the web service environment and its deploy template.
Backward compatible? yes (503 becomes real answers; merchant accounts are empty for a new tenant: the screens must show their empty states).

### 2. Comma-separated array query parameters are never split by the api  (To: C0 core pipeline, then each module) (verified by probe, 5 screens)
Problem: the contract declares these filters as arrays in style form with explode false (comma separated). The web sends `a,b,c`; the pipeline's ajv (`services/api/src/core/openapi.ts`, options at :79-85, strict query hook at :161-163, `coerceTypes: 'array'`) wraps one value into an array and never splits at commas, so `status=pending_enrolment,active,revoked` fails the enum and the maxLength (probe: `querystring/status/0 must be equal to one of the allowed values`). Screens: /instruments/agents (`listAgents` 400, default `pending_enrolment,active,revoked`, `features/instruments/server/types.ts:17,30`), /instruments/instruments (`listInstruments`, default `draft,commissioning,live,suspended`, `types.ts:131,142`), /inventory/alerts (`listInventoryAlerts`, `status=open,acknowledged`), /engagement/bookings (`listBookings`, `features/engagement/server/booking.server.ts:65`; the web's default status values should also be checked against the contract enum; `slot_start_from` and `slot_start_to` are required by the contract).
A related defect: a SINGLE value arrives as the array `['open']` and the handler rule `statusCsv` wants a string (`services/api/src/modules/inventory/handlers/alerts.schemas.ts:9`, :13-17): /inventory home (`listInventoryAlerts` 400 after the permission check, four calls per page).
Proposed change: split `explode: false` array parameters at commas once, in `core/openapi.ts` before validation (this clears all four screens), and make `alerts.schemas.ts` accept an array. Alternative: the web sends repeated parameters.
Backward compatible? yes.

### 3. Three billing list operations lose `limit` and `cursor` through YAML aliases  (To: C4 billing, contracts owner) (verified by probe through the real contract loader, 3 screens)
Problem: `contracts/openapi/billing.yaml:6803-6804` (`listPartyDiscountSlabs`), `:7184-7185` (`listUserDiscountLimits`) and `:7330-7331` (`listDiscountAuthorities`) take Cursor and Limit through the aliases `*a1` and `*a2`; after the api's own spec load those parameters are gone, so the strict query validation rejects `limit` (`querystring must NOT have additional properties`) and the web always sends `limit=200`. Screens: /billing/discounts/slabs, /limits, /authorities (400 `common.validation_failed`, db_count 0). `listDiscountReasons` (:6565) and `listInvoices` use explicit refs and accept `limit`.
Proposed change: replace the aliases by explicit `$ref: _common.yaml#/components/parameters/Cursor` and `/Limit` as in `listDiscountReasons`; and find out why the loader drops aliased parameters (it may hit other operations).
Backward compatible? yes.

### 4. `ctx.now()` is an ISO string but modules treat it as a Date  (To: C0 core pipeline, lab, micro, frontdesk owners) (verified: 2 screens, one fixed on the host)
Problem: the pipeline's `ctx.now()` returns an ISO string (`core/pipeline/index.ts:169`), typed and used as Date in several modules. `listPendingItems` (`.getTime()`) caused the /lab/pending 500: FIXED on the host by night25 (api r6: `lab/service/worklist.service.ts` normalises the clock). Still open: /micro/worklist (`listCultures` 500 `common.internal`, db_count 3: `micro/service/chain.service.ts:52` `nowOf` typed Date and :151 `now: now.toISOString()`; expected `TypeError: now.toISOString is not a function`; the repository SQL itself runs; proven by reading plus a SQL probe, not by reproducing the throw, because err_name is redacted in the logs). Other `nowOf` users: `chain.service.ts:210`, `culture.service.ts:129`, `instrument-record.service.ts:34` (wraps in `new Date(...)`, fine). Night25 also warned that the lab write paths (specimen collect and receive, signoff, label print, result service, downtime back-entry) type `ctx.now()` as Date.
Proposed change: one durable fix: type the ctx clock as it really is, or give every module one clock wrapper (night19's `withCtx` helper `core/ctxOverride.ts` is a start; CR-011 item 3); patch `chain.service.ts` now; add a unit test whose ctx is frozen and clocks with an ISO string.
Backward compatible? yes.

### 5. Handlers that accept `limit` only as a numeric string  (To: smartreport and reporting owners) (verified, 1 screen open, 1 fixed on the host)
Problem: the contract validator injects `limit` as the number 50 (default or coercion). `smartreport/handlers/summaries.ts:129-130` accepts only a numeric string and answers 400 (`listSmartSummaries`, /smartreport/summaries). `listCriticalAlerts` had the same defect: FIXED on the host by night25 (`reporting/handlers/reports-read.handlers.ts` accepts a numeric limit; /reporting). A grep of `modules/` found no other handler left with this pattern.
Proposed change: accept a number as `smartreport/handlers/library.ts:43` does; take the night25 reporting fix (`patches/DEPLOY-AXIS-NIGHT25.patch`) and its test.
Backward compatible? yes.

### 6. The web sends query parameters the contract does not have  (To: C9 web, C16 engagement) (verified, soft-failing mostly)

(b) Six web calls send `GET /v1/identity/centres?limit=200` (billing discount slabs, billing accounts, micro filter, engagement content x2, quality TAT filters); the contract has no `limit` there: 400, soft-failed, so centre lists are empty. A ready patch is `patches/NIGHT25-WEB-PROPOSED.patch` (not applied). (c) `listInventoryCodedSet` 400 (7 in the log): the web sends `?limit=200` (`features/inventory/server/read.server.ts:49,107`) but the contract allows only `reason_group`; fails soft.
Proposed change: drop the parameters in the web (filter in the BFF), or add them to the contracts if the screens need them; add a contract-versus-web query check to the web tests so this class fails in CI.
Backward compatible? yes.
