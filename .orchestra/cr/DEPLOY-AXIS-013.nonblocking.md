Title: CR-C1-DEPLOY-013: the patient mobile app cannot reach its API: no engagement operation is marked public, so the edge allowlist drops every /v1/engagement/* call on the api origin
From chunk: C1 (deploy attempt, prod-lean, 2026-11-23; found while connecting apps/patient_app to the test server with the Antigravity coding agent)    To owner: per item (listed below)
Type: bug
Blocking? yes for any use of the patient mobile app against a deployed edge (the app cannot start its first call); no for any current orchestra task, so this file is named `.nonblocking`.
Relation to earlier CRs: CR-C1-004 (edge allowlist generated from `x-edge-exposure`), CR-C1-T13 (SEED list); 08 A19 D-122 (OTP zone). CR-012 covers the staff web screens; this CR covers the mobile apps.

## Evidence from the host
Test host (api origin `api.lmis.imisaxis.com`, reached over Tailscale 100.82.8.12:8443 with the internal CA; TLS validates, ALPN http/1.1):
- `GET /v1/engagement/app/config` with `X-Lims-Patient-PreAuth: t.demo_lab4` answers `404 Not Found` with an nginx HTML body (not problem+json): the edge never forwarded it. The app shows "We can't reach Demo Lab (dev) right now".
- Control: `POST /v1/identity/mobile/sessions` (an allowlisted route) answers `400 common.validation_failed` as problem+json: the path to the api works.
- `infra/edge/public-routes.yaml` (generated by `infra/ci/gen-routes.sh` from operations marked `x-edge-exposure: public`) has 12 routes: identity patient session resolve/logout, identity mobile sessions, instruments agent, payments callbacks/launch/result, reporting provider callbacks. `contracts/openapi/identity.yaml` has 15 `x-edge-exposure` marks; `contracts/openapi/engagement.yaml` has 0 marks on its 100 operations. The api vhost template (`infra/edge/nginx/sites/api.conf.j2`) denies everything not in the list (`location / { return 404; }`).
- The patient app calls 17 distinct engagement paths (`apps/patient_app/lib/features/**`): `/v1/engagement/app/config`, `/v1/engagement/auth/otp-challenges` and `/verify`, `/v1/engagement/me` and `me/profiles`, `me/orders`, `me/reports` (+ file, smart-summary), `me/payment-requests`, `me/notifications`, `me/memberships`, `me/enquiries`, `me/coded-sets/{set}`, plus identity patient session resolve and logout (those two ARE allowlisted).

## Items

### 0. The api never wires the module auth resolvers: every operation under patientPreAuth, portalSession, queueDisplayToken and deviceToken always answers 401  (To: C0 core, C16 engagement, C6 reporting, C7 instruments) (verified live and in the code; this is the real blocker)
Problem: after the interim edge change (item 6) the app's first call reaches the api and still fails. Live probes on the test host, 2026-11-23 04:01 UTC, `GET /v1/engagement/app/config` with `X-Lims-App-Version`, `X-Lims-App-Platform` and `X-Lims-Patient-PreAuth: t.<code>`: `demo_lab4` (active), `demo_lab3` (active), `demo_lab` (provisioning) and `nosuchtenant` ALL answer `401 auth.unauthenticated` (request ids 01a20690-fd2c-70f3-9009-f7e297227415, 01a20690-fd53-79dc-a6fb-e7794fbb7596, 01a20690-fd74-71e4-ba44-0732ab931591, 01a20690-fd93-71f1-ae5a-6d233e29663b), duration 1 ms, `db_count` 0: the tenant lookup never runs. The tenant is active, `lims_api` holds EXECUTE on `app.core_resolve_tenant_code` and the database logged no error.
Cause (code): `services/api/src/core/openapi.ts` `securityHandlers(auth)` registers only `bearerJwt` and `bffSession`; its comment says "Schemes without a handler here fail closed (glue rejects the request)". `core/auth/resolvers.ts` `createAuthResolverRegistry` (which would call `engagement/auth/preauth.resolver.ts` for `patientPreAuth`) is referenced only by tests (`engagement/__tests__/preauth.resolver.test.ts`, `display.*.test.ts`, `reporting/__tests__/portal.*`, `instruments/.../device-credentials.test.ts`); `core/bootstrap.ts` builds `CoreAuth` without it. So the four module-owned schemes `patientPreAuth`, `queueDisplayToken`, `portalSession` and `deviceToken` have no runtime handler.
Impact: the patient mobile app can never get past its first call; the same wiring gap would stop the patient report portal links (portalSession), the queue display board (queueDisplayToken) and the instrument bridge agent (deviceToken): check each on a deployed stack. The unit tests passed because they build the registry themselves.
Proposed change: in `bootstrap.ts` build the registry from the mounted modules (`createAuthResolverRegistry(modules.map(m => m.manifest))`), pass it in `CoreAuth`, and in `securityHandlers` add one handler per registered key that reads the credential from the scheme's declared location (apiKey header or cookie from the contract), calls `registry.authenticate(key, credential, tx)` and stores the resulting claims like `bearerJwt` does; add an integration test that boots the real app with the engagement module and gets 200 (not 401) on `getPatientAppConfig` for an active tenant and 401 for an unknown one.
Backward compatible? yes (operations that always answered 401 start to authenticate); security review required: this is the authentication path for anonymous and device callers.

### 0b. Patient sign-in cannot complete even with a correct code: the identity patient writers and the patient JWT signer are not wired  (To: C2 identity, C0 core, C16 engagement) (verified live and in the code, 2026-11-23)
Problem: after item 0 was bridged host-only (api r9: the `patientPreAuth` resolver wired; api r10: a demo-only fixed code for one synthetic phone on the demo tenant) and the tenant setting `app_enabled` was turned on for `demo_lab4`, the full flow on the test host gives: `GET /v1/engagement/app/config` 200 (`features.app` true), `POST /v1/engagement/auth/otp-challenges` 202, `POST /v1/engagement/auth/otp-challenges/verify` with the matching code answers `500 common.internal` (api log: `verifyPatientOtp`, `db_count` 5, request id 01a207e4-9c52-75d0-8132-40cbd4adf19d; no database error is logged: `supabase-db` shows only the unrelated WAL archive line), and a WRONG code on a new challenge answers the expected 401 `auth.otp_invalid`. So the code check passes and the step after it fails.
Cause (code): `engagement/service/auth.service.ts` `verifyOtp`, after the match, calls `ctx.ports.IdentityPort.provisionPatientMembership` and `openPatientSession`; any failure there is mapped to a bare `common.internal` (by design: the transaction rolls back and the code stays usable). In `identity/index.ts` the port is built as `createIdentityPort({ repo: createCoreAdminRepo(), systemActorPermissions: () => [] })` with the comment "LD-81: no mintPatientAccessToken and no patient writers here: openPatientSession / provisionPatientMembership throw common.internal 'not wired'". `IdentityPort.impl.ts` throws `unwired()` when `repo.createPatientMembership`, `repo.insertPatientSession` or `deps.mintPatientAccessToken` is absent; `identity/handlers/resolvePatientSession.ts` carries a placeholder signer that throws "identity: patient JWT signer not wired" (line 28). None of the three exists outside the type declarations. So no patient can ever be signed in on any deployment of main, SMS or not.
Impact: the patient mobile app (and any other patient session) cannot sign in. The patient report portal, which uses a different scheme, is a separate question.
Proposed change: implement `createPatientMembership` (idempotent per account id, user id generated by LIMS, no phone or e-mail) and `insertPatientSession` in the identity repo, a patient access-token signer (the 1 h JWT of LD-81, signed with a key the verifier trusts: decide key source and rotation), pass them to `createIdentityPort` and the session handlers, and add an integration test that runs requestPatientOtp -> verifyPatientOtp -> getMyAccount against a real database (the unit tests pass because they fake the port). Security review required (token minting).
Backward compatible? yes (operations that always answered 500 start to succeed).
Interim state on the test host: app_enabled true for demo_lab4 only (row version 2), api r10 with a demo-only shortcut for one synthetic phone (host-only, never to merge); neither helps sign-in until this item lands. Remove the shortcut (roll back to api r9) if the app is not going to be used.

### 1. Mark the patient-app operations `x-edge-exposure: public`  (To: C16 engagement, contracts owner C0) (verified)
Problem: none of the 31 patient-facing operations in `engagement.yaml` carries `x-edge-exposure: public`: `getPatientAppConfig`, `requestPatientOtp`, `verifyPatientOtp`, `getMyAccount`, `updateMyAccount`, `deleteMyAccount`, and every `/me/*` operation (profiles, self-registrations, orders, reports and downloads, bookings, bookable-items, booking-centres, slots, addresses, payment-requests, notifications, memberships, enquiries, coded-sets, portal-content). The staff operations of the same file (`/membership-plans*`, `/memberships*`, `/app-links/{id}/revoke`) must stay internal.
Proposed change: add the mark to exactly those operations; regenerate `infra/edge/public-routes.yaml`; the CI job `edge-routes-drift` then passes.
Backward compatible? yes (adds routes; the allowlist stays default-deny).

### 2. `gen-routes.sh` needs TABLE entries for the new public prefixes  (To: C1 edge) (verified in the script)
Problem: the TABLE already has `("/v1/engagement/auth/otp-challenges", "prefix", "C16", 3, "otp", None)`, but templated paths without a TABLE entry fail closed (`route_for` returns None for paths containing `{`), and `/v1/engagement/app/config` and `/v1/engagement/me...` have no entry.
Proposed change: add `("/v1/engagement/app/config", "exact", "C16", 3, "otp", None)`, `("/v1/engagement/me", "exact", "C16", 3, "psession", None)` and `("/v1/engagement/me/", "prefix", "C16", 3, "psession", None)` (zones as the owner decides, see item 3). Beware the prefix `/v1/engagement/app` would also match the staff path `/v1/engagement/app-links/...`: use the exact form for app/config.

### 3. Rate zones for authenticated mobile traffic  (To: C1 edge, C16) (reported)
Problem: the only per-IP zones that fit are `psession` (120 r/m per IP) and `otp` (60 r/m per IP); a mobile carrier gives many patients one NAT address, so 120 r/m for all `/me/*` calls of every patient behind one address is tight, and `report_download` has its own tier in the contract but no edge zone.
Proposed change: decide zones per operation group (key by the patient JWT subject or app instance where the edge can, else raise the rate); add a zone for report downloads and a body limit for the POST routes.

### 4. A sign-in code cannot be delivered in a demo or test environment  (To: C16 engagement, C1) (verified by reading `engagement/service/auth.service.ts`)
Problem: `requestOtp` checks the tenant setting `app_enabled` (`common.feature_disabled` when false) and the allowed phone prefixes, stores the encrypted challenge and queues the job `engagement.send_login_otp`, which sends by SMS or WhatsApp. On the demo tenant `demo_lab4` both channels are deliberately off, so no code arrives; there is no documented test or sandbox OTP mode in `engagement.yaml` or the code (the Antigravity agent reported a setting named `ENGAGEMENT_OTP_TEST_CODE`: it does not exist in the repository at origin/main).
Proposed change: provide a supported test mode that cannot run in production (for example fixed codes only for configured test phone numbers when the core environment is not production), or document the SMS provider sandbox setup for a demo tenant; state the default of `app_enabled` for a newly provisioned tenant.

### 5. Nothing checks the mobile apps against the edge allowlist  (To: C1, C16, C17) (reported)
Problem: this gap went unnoticed because no test compares the API paths used by `apps/patient_app` and `apps/phlebo_app` with `public-routes.yaml`. The phlebo app's calls other than `/v1/identity/mobile/sessions` were not enumerated here.
Proposed change: add a CI check that extracts every `/v1/...` path used by the two mobile apps (or their generated clients) and fails when one is neither in the allowlist nor marked internal in the contract.

### 6. Interim host-only change (recorded, to be dropped when item 2 lands)  (To: C1) (applied on the deploy host by the unattended run night32; see its report)
The deploy copy's `infra/edge/public-routes.yaml` gets four entries: `/v1/engagement/app/config` (exact, GET, zone otp), `/v1/engagement/auth/otp-challenges` (prefix, POST, zone otp), `/v1/engagement/me` (exact, GET and PATCH, zone psession) and `/v1/engagement/me/` (prefix, GET, POST, PUT and PATCH, zone psession), owner C16, phase 3. The edge is reloaded, not restarted. Remove the entries when the regenerated file ships.

Tenant/security impact: item 1 and the interim change expose the patient API (pre-auth and bearer-JWT routes) on the api origin; they are authenticated by the app's patient JWT and rate limited per IP; nothing else of the api becomes reachable (default deny stays). No PHI in this CR; no secret value appears.
IRD/regulatory impact: none.
Alternatives considered: serving the mobile apps through the portal BFF (rejected by the design: the apps use bearer JWT on the api origin, 02-TRD §3.5); leaving the routes unexposed and testing only on a local stack (the apps could then never be tested against a real edge).
Tests that will prove it:

- the mobile-versus-edge CI check of item 5;
- host smoke from the tailnet: `GET /v1/engagement/app/config` with the pre-auth header answers from the api (200 or a problem+json), `GET /v1/engagement/me` without a token answers 401 problem+json, `GET /v1/engagement/membership-plans` still answers 404 from nginx, `POST /v1/engagement/auth/otp-challenges` with an empty body answers 400 problem+json.
