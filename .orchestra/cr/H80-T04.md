Title: CR-C7-018: core uploads must re-encode image/jpeg (strip metadata) or ingest cannot store the H80E chromatogram
From chunk: C7            To owner: C0-0C (core uploads)
Type: shared-lib
Blocking? yes for production use of H80-T04 (code + tests are done; with `images.reencode` a JPEG is refused). Not blocking T04 tests (they use a spy for JPEG).
Problem: 08-ADDENDUM-TRUTH-H80E §3 says the chromatogram is a base64 JPEG (`/9j/`) and must be stored with re-encode + strip metadata + scan (§6.8 step 2). `core/uploads/index.ts` accept() only re-encodes PNG: `if (mime !== 'image/png') throw new ImageRejected()` -> `common.upload_quarantined` for every JPEG when `images` is set. So the real chromatogram is always rejected. REQ-SEC-083..085.
Proposed change (exact): in `core/uploads/image.ts` add `reencodeJpeg(bytes, maxMegapixels)` (decode, drop APP/EXIF/COM segments, re-encode; ImageRejected on a bad or oversize image) and call it in accept() for `image/jpeg` when `opts.images` is set. No signature change.
Backward compatible? yes (only JPEG with `images` changes, today always rejected).
Tenant/security impact: none new; closes EXIF/GPS leak path for JPEG. No new PHI field.
Alternatives considered: (a) drop `images` for the inline path: rejected, leaves metadata unstripped (REQ-SEC-084). (b) convert JPEG to PNG in the driver: changes the stored type, loses fidelity.
Tests that will prove it: core uploads test with a JPEG carrying planted EXIF/GPS: stored object has no marker; a corrupt JPEG -> `common.upload_quarantined`.
