Title: CR-C17-PHLEBO-UI-FULL-1: contract gaps found while building the complete phlebotomist app UI (travel stage, live location, alerts feed, history, support report, tube-cap tokens) and two board items the spec already rules out

Type: api | event | ui-kit | bug
Blocking? no for the UI (every item below is shown in the app today through a callback or a dev-only synthetic source and writes nothing); yes for wiring each item to real data.
Problem (what you cannot do today, with the user story / acceptance criterion it serves):
The founder asked for the phlebotomist app UI "A to Z" in the MyHealthNow patient-pack look, including what the patient app (C16: S28 collector not assigned, S29 collector assigned, S30 live tracking and its delayed/lost/offline states, S31 collector arrived, S32/S32a collected/partly collected, S33 sample journey) and the dispatch web screens (C17 W1–W5) expect from the collector. The screens are built (apps/phlebo_app, shell + 48 gallery states). These parts have no contract name yet, so they are NOT wired and NO name was invented:
 1. Travel stage "On my way": C16 S29/S30 show Assigned > On the way > Arrived > Collected. C17 has only `visit.arrived` (03-APP-FLOW §4). Need a visit stage "on the way" the phone can set before arrival (mutation type + patient-visible status).
 2. Live location while on the way (S30 and its states S30a delayed, S30d lost, S30b unavailable, S30e/f offline): C17 only captures one GPS point at arrival (W5 "Capture GPS point", CR-C17-010 pending). Need a position stream or periodic update, a retention rule, and the end-of-sharing rule (stop at `visit.arrived`). The phone-side states are drawn (`LocationSharing`: live, delayed, noSignal, permissionOff).
 3. Alerts feed (Alerts tab): new visit, route reorder, cancel, recollection, dispatcher message. The PRD says there is no push (out of scope list), so the tab is meant to be built from the sync diff; a "dispatcher message" kind needs a field/endpoint if wanted.
 4. History (History tab): last working days with outcome per visit. No pull of closed visits is defined and the 03-APP-FLOW purge rules would clear them. Need: retention window on the phone and what a closed visit snapshot may keep (patient name is on the board).
 5. Support report ("Report a problem", patient-pack S50 equivalent) and "Contact dispatch": no endpoint, no centre contact in the snapshot/config. UI takes a callback and a `DispatchContact`.
 6. Tube cap colours: the design tokens have no tube-cap colours (EDTA, plain, SST, fluoride, urine). The app maps container text to the nearest tone and always prints the container name. Request a small token set in packages/ui (C0-0D) if the board's coloured dots are wanted.
 7. Two board items that the spec already rules out, NOT built: (a) "Label printer / Print" (M5 Profile + Collection complete): D-LABELS (01-PRD §4.3) says tubes are labelled at the centre and the phone only scans; field printing is out of scope. (b) "Notification preferences": no push exists. Please confirm they stay out, or open a PRD change.
 Also noted: M1 sign-in. The M5 board draws Staff ID + 4-digit PIN; 04-UI-UX §3.1 and 03-APP-FLOW §3 say email + password. The app follows the spec (email, password, screen-lock gate, fingerprint unlock for a valid session). Please confirm.
Proposed change (exact): items 1–5 need C0-0C decisions (OpenAPI diff + event/mutation names) and a C17 02-TRD §6.3 row each; item 6 is a tokens.json addition. Until then: item 1 `onStartTravel`, item 2 `TravelState.sharing`, item 3 `PhleboAlert`, item 4 `HistoryDay`, item 5 `ReportProblemScreen.onSubmit` / `DispatchContact` are the seams the real shell fills. No endpoint, event, table or permission name was added by this work.
Backward compatible? yes — additive; the existing mutation types and screens keep their behaviour (every existing phlebo_app test still passes except the 2 scan_apk tests that already fail on a pristine HEAD in this sandbox).
Tenant/security impact: item 2 adds location data (new PHI-adjacent field, REQ-SEC-109/111 review, retention); item 4 keeps patient names on the phone longer than a route day (purge rules); item 5 free text must carry no patient data (screen warns). No RLS change in this UI work.
IRD/regulatory impact: none.
Alternatives considered: inventing mutation/endpoint names in the app (rejected: CLAUDE.md, never invent names); hiding the travel/alerts/history screens until contracts exist (rejected: the founder asked for them, and the callbacks make them contract-neutral); building field printing from the board (rejected: D-LABELS).
