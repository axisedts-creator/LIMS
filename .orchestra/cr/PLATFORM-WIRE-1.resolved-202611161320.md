Title: CR-C1-PLATFORM-WIRE-1-001: stage 9 authz guard 500s every platform 2xx outside production (no platform service calls IdentityPort.assertRole)
From chunk: C1            To owner: C0-0D (core/ports/authz-guard.ts, core/pipeline) with C2 (identity platform services)
Type: bug
Blocking? yes: PLATFORM-WIRE-1 done_when "reaches its service" is met, but the console still gets HTTP 500 on staging for every platform operation (8 cases of "end to end status" in services/api/src/modules/identity/__tests__/platform-wire.operations.test.ts stay red; not weakened).
Problem: core/ports/authz-guard.ts check() throws common.internal (every env but production) for a 2xx of a non-public operation whose handler never called IdentityPort.assertRole. Platform services authorise with PlatformAuthz.assertPlatform only (02-TRD 5.10, 7.2 step 3), so no platform handler ever sets `asserted`. After the PLATFORM-WIRE-1 field fix the service runs and returns 2xx, then stage 9 turns it into 500 (this is also the real cause behind the listDeadLetters 500 of 2026-11-16 09:56 NPT, request id 01a1e28d-5276; the service ran). Production only logs `authz_not_asserted` and returns the 2xx.
Proposed change (exact, not done by C1; PlatformAuthz semantics unchanged, no new authority): in identity module, IdentityPort.assertRole(ctx, req) with ctx.platformRole set and req.permission starting `platform.` delegates to PlatformAuthz.assertPlatform(ctx, req.permission) (same check, same errors); each platform service guard (tenant/ird/support/dead-letter/platform-staff) calls ctx.ports.IdentityPort.assertRole(ctx, { permission }) instead of calling PlatformAuthz directly (or in addition, first). Pipeline wraps the port already, so `asserted` flips. Option B (rejected by C1: weakens the guard): exempt x-context platform operations from stage 9.
Backward compatible? yes (tenant sessions unchanged; unknown_permission still refused for non-platform callers).
Tenant/security impact: none new; RLS unchanged; keeps one authz decision point per operation (REQ-SEC-067 aal2 for privileged codes stays in PlatformAuthz).
IRD/regulatory impact: none.
Alternatives considered: Option B above; production-only behaviour (what runs today) hides the defect on staging.
Tests that will prove it: the 8 red cases of "end to end status" in platform-wire.operations.test.ts (200 for superadmin aal2 and platform_support aal2, `authz_not_asserted` not logged).
