## C5-lab-workflow (main)
Title: CR-C5-T01: core ajv rejects the `x-coded-set` schema annotation, so no module whose spec uses it can boot
From chunk: C5            To owner: C0-0D
Type: bug
Blocking? yes — C5 T-01 done_when "API boots with all operationIds bound against lab.yaml" (06-IMPLEMENTATION-PLAN row T-01).
Problem: `bootstrap()` with the real lab module fails: `FastifyError: Failed building the validation schema for POST: /v1/lab/specimens/:specimen_id/reject, due to error strict mode: unknown keyword: "x-coded-set"`. The validators built in `services/api/src/core/openapi.ts` (`schemaController` + `installRouteHooks` response compile, via `@fastify/ajv-compiler` with `AJV_OPTIONS`/`BODY_AJV_OPTIONS`/`RESPONSE_AJV_OPTIONS`) run ajv in strict mode and do not know the annotation. `x-coded-set` appears inside schemas of analytics, billing, catalog, frontdesk, instruments, lab, reporting .yaml — every one of those modules fails boot the same way.
Proposed change (exact): in `services/api/src/core/openapi.ts` add `keywords: ['x-coded-set']` to `AJV_OPTIONS` (inherited by body/response options). Keeps strict mode for every other unknown keyword. (Same class of gap as the `x-extensible` dispute T0C-01; if that keyword can reach request/response schemas, register it too.)
Backward compatible? yes — annotation only, no validation semantics.
Tenant/security impact: none; strict mode stays on (REQ-SEC-080 unaffected, removeAdditional stays false).
IRD/regulatory impact: n/a
Alternatives considered: stripping `x-*` keys in the module (C5 does not own the mount path; would hide spec drift); `strictSchema: false` (too broad).
Tests that will prove it: C5 `services/api/src/modules/lab/__tests__/boot.test.ts` "boot against the real repo" (2 tests); a core openapi test mounting a fixture schema with `x-coded-set`.
