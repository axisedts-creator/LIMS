Title: CR-C3-T04: trim `sort` enum of listSpecimenTypes / listContainers / listMethods to `code`, `name` (no `report_order` column)
From chunk: C3            To owner: C0-0C (contracts/openapi/catalog.yaml; doc owner for C3 02-TRD §5.2 #5–8)
Type: api
Blocking? no — T-04 ships with the service rejecting `sort=report_order` on these three lists with 400 `common.validation_failed`.
Problem: 02-TRD §5.2 rows 5–8 give one `sort` list (`code`,`name`,`report_order`) for every R, and catalog.yaml copies the departments enum to all four list operations. Only `departments` has a `report_order` column (02-TRD §5.1 `Department`; `SpecimenType`, `Container`, `Method` have none). So a contract-valid `GET /v1/catalog/specimen-types?sort=report_order` cannot be served (AC-01.1–01.4 list reads).
Proposed change (exact): in contracts/openapi/catalog.yaml remove `- report_order` and `- -report_order` from the `sort` query parameter enum of `listSpecimenTypes` (~line 569), `listContainers` (~line 782) and `listMethods` (~line 1005). Keep `listDepartments` (~line 351) unchanged. In C3 02-TRD §5.2 rows 5–8 change the sort note to "`code`,`name` (+ `report_order` for departments)".
Backward compatible? no in the strict oasdiff sense (enum values removed from a request param), but no client can use the values today: the server already returns 400. No consuming chunk affected (C3 owns these endpoints; web UI not yet built).
Tenant/security impact: none (no RLS, no PHI, no new surface).
Alternatives considered: (a) define `report_order` for these tables (new DDL columns; no AC asks for it); (b) silently fall back to `code` sort (hides a client error; violates 02-CV error rules).
Tests that will prove it: add a contract check that, for each of the four list operations, the catalog.yaml `sort` enum (minus `-` prefixes) equals the service's `sorts` in `services/api/src/modules/catalog/service/masters.service.ts`; existing `masters.handlers.test.ts` stays green.
