Title: CR-C1-T11: (a) replica rsync uses `--partial-dir=.rsync-partial` instead of bare `--partial`; (b) no task owns the dr-side `replica` chroot account
From chunk: C1            To owner: C1 (lead)
Type: gap
Blocking? (a) no. (b) yes for an end-to-end run in staging/prod of T-11 (object replica) and of pgBackRest repo2 over SFTP (T-09). Static T-11 tests pass.
Problem:
(a) 02-TRD s9.5 gives `rsync -a --ignore-existing --partial ...`. With bare `--partial`, rsync keeps an interrupted file under its FINAL name on the replica (rsync(1)). The next 15-min run then skips it because of `--ignore-existing`, so a truncated object stays on dr forever, the lag metric reads 0 (AC-14.2 green with a broken copy), and only the nightly verify flags it, every night, with no repair (AC-14.3). 03-APP-FLOW expects "partial transfer (`--partial` resumes)".
(b) 02-TRD s3 port table names "chroot accounts" on dr sshd :2222. No task in 06-IMPLEMENTATION-PLAN creates the `replica` user, the sshd :2222 chroot (/replica -> /srv/lims/replica), or its authorized_keys (public half of secret id `object_replica_ssh_key`). The same gap exists for the pgBackRest repo2 SFTP account. T-11 only creates /srv/lims/replica/storage on dr.
Proposed change (exact):
(a) Amend 02-TRD s9.5 command line to `rsync -a --ignore-existing --partial-dir=.rsync-partial --checksum-choice=xxh128 -e "ssh -p 2222 -i ..." /srv/lims/storage/ replica@dr-1:/replica/storage/`. `--partial-dir` implies `--partial`, keeps the resume, and keeps the half file out of the final name. Already in `infra/ansible/roles/object_replica/files/lims-object-replica.sh`.
(b) Assign to one C1 task (suggest a new row, or T-09/T-11 extension): on group `dr` (lean: backup-1, LD-45) create a dedicated sshd instance on :2222 bound to the wg0 IP, `Match User replica` + pgBackRest repo2 user with `ChrootDirectory`, `ForceCommand internal-sftp` for SFTP or rrsync-restricted command for rsync, `AllowTcpForwarding no`, `PermitTTY no`; install authorized_keys from the public keys of `object_replica_ssh_key` and the repo2 key. Also: inventory var `object_replica_host_key` ("<type> <base64>" of that sshd host key) must be set per environment in staging/prod group_vars; the role asserts and fails closed until it is set.
Backward compatible? yes (a: flag change only; b: additive).
Tenant/security impact: no RLS / PHI-field / public-surface change. (b) is a new SSH surface on wg0 only; chroot + forced command + key-only auth limit it to the replica dirs. Host key pinning (StrictHostKeyChecking=yes) stays.
Alternatives considered: (a) keep bare `--partial` and repair in nightly verify - verify is read-only by design and would rewrite existing replica files, which the ransomware rule (`--ignore-existing`) forbids. (b) reuse the normal sshd :22 - mixes admin and service access, no chroot.
Tests that will prove it: (a) `test_flags_use_partial_dir_not_bare_partial`, `test_interrupted_transfer_is_completed_by_next_run_or_shown_as_lag` (infra/tests/static/test_t11_object_replica.py), both pass. (b) staging run: `systemctl start lims-object-replica` succeeds, file lands in /srv/lims/replica/storage on dr, `replica` cannot open a shell or leave the chroot.
