Title: CR-C3-T18: TaxType.effective_from / version for the global VAT row (scope: global)
From chunk: C3            To owner: C3 (contracts/openapi/catalog.yaml TaxType) / C0-0B (g_tax_types)
Type: api
Blocking? no for T-18 tests (all pass); yes for closing the review item on pricing.service.ts globalTypeDto.
Problem: GET tax types (#86) returns the global VAT row from g_tax_types. OpenAPI `TaxType` (contracts/openapi/catalog.yaml:10954) requires `effective_from` (and `version`), but g_tax_types has no effective_from/version column. 08 A4.1 (08-CR-REGISTER.md:1957) forbids deriving the VAT effective date from `created_at`. The code currently reports created_at and version 1 — an invented value (AC-15.2, AC-15.5).
Proposed change (exact): in `TaxType`, make `effective_from` and `version` not required when `scope: global` (oneOf/discriminator on `scope`, or drop both from `required` and document "absent for scope=global"). Implementation then omits both for the VAT row.
Backward compatible? yes for the response shape of tenant rows; clients reading `effective_from` on the VAT row must accept absence (C-web catalog screens only).
Tenant/security impact: none (no RLS change, no PHI, no new surface).
IRD/regulatory impact: none — VAT rate itself unchanged; only the reported date metadata.
Alternatives considered: (a) add effective_from/version columns to g_tax_types (schema CR to C0-0B; heavier); (b) keep created_at (rejected by 08 A4.1).
Tests that will prove it: surchargeTax.handlers.test.ts OpenAPI-validated list of tax types with the VAT row lacking effective_from/version.
