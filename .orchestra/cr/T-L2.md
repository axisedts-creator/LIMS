Title: CR-C16-T-L2: (1) per-patient link count for E14 under PAT_ACC RLS; (2) US-EN-03.4 re-redeem by the same account (422 vs 200)
From chunk: C16            To owner: C16 (05-SCHEMA §6.1 / 01-PRD US-EN-03) — arbiter ruling needed
Type: schema (1); bug / spec conflict (2)
Blocking? yes — T-L2 (06-IMPLEMENTATION-PLAN row T-L2) on US-EN-03.8 (1) and US-EN-03.4 (2).
Problem:
 (1) E14 (02-TRD §4.3.2 step 4, US-EN-03.8) must reject a new link when the patient already has `max_accounts_per_patient` active links. link.service.ts redeem calls `repo.activeLinkCount` (`count(*)` on `engagement.account_patient_links`) inside the patient's transaction. 05-SCHEMA §5 gives a patient only PAT_ACC (`account_id = app.engagement_account_id()`), so the count sees at most the caller's own link; the limit is never enforced in prod. The test world (`__tests__/link.world.ts:216`, marked ASSUMED) counts tenant-wide, so the API tests pass. No DEFINER for this count is named in the spec.
 (2) 01-PRD US-EN-03.4: "A1 again -> 200 returning the existing link, idempotent". The DEFINER `app.engagement_redeem_link_code(bytea)` (05-SCHEMA §6.1) updates only `c.status = 'issued'`, so a redeemed code returns no row and E14 answers `422 engagement.link_code_invalid` (link.service.ts) and counts a failure. No test pins the AC.
Proposed change (exact):
 (1) Option A (preferred): add the check inside `app.engagement_redeem_link_code(bytea)` after the UPDATE: when no live link of `v_account` exists and `(SELECT count(*) FROM engagement.account_patient_links l WHERE l.tenant_id = c.tenant_id AND l.patient_id = v_code.patient_id AND l.status IN ('active','suspended')) >= s.max_accounts_per_patient`, return a row with a new column `limit_reached boolean` (service maps it to `409 engagement.link_limit_reached` and the throw rolls the redemption back). Option B: new `SECURITY DEFINER app.engagement_patient_link_count(p_patient_id uuid) RETURNS int` (same tenant predicate, EXECUTE to the patient role), called by `repo.activeLinkCount`.
 (2) Either (a) amend US-EN-03.4 to "422 for every account" (code as built), or (b) extend the DEFINER: when no 'issued' row matches but a 'redeemed' row with `redeemed_account_id = v_account` matches the hmac, return the existing link (service already answers 200 when `existing_link_id` is set) and do not count a failure.
Backward compatible? yes — additive (new column / function, or AC text change).
Tenant/security impact: (1) DEFINER must bind `app.current_tenant_id()` and return only a count (no PHI, no other account ids). (2b) must not reveal anything to a different account (still identical 422).
IRD/regulatory impact: n/a
Alternatives considered: counting via the API role outside RLS (rejected: patient path must run under RLS, 07-SECURITY); leaving the world's tenant-wide count (hides the prod defect).
Tests that will prove it: pgTAP — patient P with N = max links from other accounts, a new account redeeming P's code gets 409 and the code stays `issued`; API — same case on the world after it emulates the chosen DEFINER; (2) API test "A1 re-redeems own redeemed code -> 200, same link id, no failure counted" or "-> 422" per ruling.
