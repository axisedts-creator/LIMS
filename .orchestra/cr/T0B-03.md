Problem (what you cannot do today, with the user story / acceptance criterion it serves):
  05-SCHEMA.md:888-889 `audit_log__actor__ck` = `(actor_id IS NOT NULL AND created_by IS NOT NULL) OR (actor_id IS NULL AND
  created_by IS NULL AND actor_type = 'system' AND detail ? 'maintenance')`. For `detail IS NULL`, `detail ? 'maintenance'` is NULL,
  so the CHECK evaluates to NULL and the row is accepted (Postgres CHECK passes on NULL). This contradicts 05-SCHEMA.md:269/275
  and 08-CR-REGISTER.md:3063 (A28.5): actor_id NULL only for maintenance rows, which carry `detail.maintenance`.
  Reproduced by writer: INSERT (actor_id NULL, created_by NULL, actor_type 'system', detail NULL) -> no 23514.
Proposed change (exact): in 05-SCHEMA §10, same constraint name:
  CONSTRAINT audit_log__actor__ck CHECK ((actor_id IS NOT NULL AND created_by IS NOT NULL)
     OR (actor_id IS NULL AND created_by IS NULL AND actor_type = 'system' AND coalesce(detail ? 'maintenance', false)))
  Update the constraint-text assertion in tests/db/T0B-03.core-tables.test.mjs to match.
Backward compatible? yes — tightening only; pre-M1, no released data; app.tg_row_audit always sets detail when actor_id is NULL (05-SCHEMA.md:1021).
