Title: CR-C0-T0B-08-T0B-02: T0B-02_helpers #56 requires a pg_default_acl row that a no-op REVOKE never creates
From chunk: C0 (T0B-08)            To owner: C0-0B (T0B-02 tests)
Type: bug
Blocking? yes — T0B-08 done_when "suites re-run on pinned supabase/postgres:17.6.1.136" (run log .orchestra/notes/T0B-08-run-r5.log).
Problem: db/tests/app/T0B-02_helpers.test.sql #56 `lims_owner default ACL for tables has no PUBLIC rights` asserts
  EXISTS (pg_default_acl row with defaclrole = lims_owner AND defaclobjtype = 'r' AND no PUBLIC grantee).
  The migration runs 05-SCHEMA §2 L133 verbatim: `ALTER DEFAULT PRIVILEGES FOR ROLE lims_owner REVOKE ALL ON TABLES FROM PUBLIC;`.
  PostgreSQL's built-in table default grants PUBLIC nothing, so that REVOKE equals the built-in default and stores no
  pg_default_acl row. The EXISTS is false even though PUBLIC holds no default table rights. The functions check (#55) passes
  because PUBLIC EXECUTE is a real built-in default, so revoking it stores a row.
Proposed change (exact): #56 becomes
  SELECT ok(NOT EXISTS (SELECT 1 FROM pg_default_acl d, aclexplode(d.defaclacl) a WHERE d.defaclrole = 'lims_owner'::regrole
    AND d.defaclobjtype = 'r' AND a.grantee = 0), 'lims_owner default ACL for tables has no PUBLIC rights');
  No migration change (05-SCHEMA §2 stays verbatim).
Backward compatible? yes (test only).
Tenant/security impact: none. The property under test (PUBLIC gets no default table rights) stays asserted.
Alternatives considered: add a dummy default GRANT to force a row (rejected: invents a grant the spec does not have).
Tests that will prove it: db/tests/app/T0B-02_helpers.test.sql #56 on the pinned image.
