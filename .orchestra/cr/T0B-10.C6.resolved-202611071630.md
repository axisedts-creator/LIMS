Title: CR-C0-T0B-10.C6: provider-callback DEFINER enqueues per_tenant task without tenant claims
From chunk: C0 (T0B-10.C6)            To owner: C0-0B (enqueue wrapper) + C6 (reporting_ingest_provider_callback)
Type: schema
Blocking? yes. T0B-10.C6 behaviour tests for C6 check 14 (provider callback) cannot pass.
Problem: `app.reporting_ingest_provider_callback` (C6 05-SCHEMA:1310-1337) is pre-tenant: it runs as lims_api with no claims and resolves the tenant from the callback token. At :1332 it calls `app.enqueue_job('reporting.apply_provider_events', {tenant_id: v_tenant}, ...)`. That task works on tenant deliveries (C6 02-TRD:810), and C6 jobs run under tenant claims (C6 02-TRD:824), so its registry scope is `per_tenant`. `app.enqueue_job` raises `job_tenant_mismatch` when `app.current_tenant_id()` IS NULL for a per_tenant identifier (C0 05-SCHEMA:1067-1069: "nothing relaxes this check"). Result: every valid provider callback fails, and the AC-09.3 callback flow is broken (C6 06-PLAN C6-T29).
Proposed change (pick one; the owners decide):
 (a) Inside the callback DEFINER, immediately before the enqueue, set tenant claims for the reporting system actor: `PERFORM set_config('request.jwt.claims', jsonb_build_object('tenant_id', v_tenant, 'sub', <reporting system actor id from core.g_system_actors>, 'actor_type', 'system')::text, true);`. Restore the previous claims after the enqueue and before every return (A21.4 style).
 (b) Move the enqueue out of SQL. The API handler calls `ctx.queue.enqueue` inside `withTenantScope(returned tenant, reporting system actor)`. The function then also returns the tenant_id (signature change to the 08 §4.7 signature).
 (c) Add a third registry scope, or a documented exemption for DEFINER-originated enqueues whose payload tenant_id came from a verified token. This relaxes the C0 invariant and is not recommended.
Backward compatible? (a) yes: body-only. (b) no: changes the 08 §4.7 / CR-C6-002 signature, and the C6 API handler breaks.
Tenant/security impact: (a) the claims are local to the transaction, built from the token-resolved tenant only, and reset before return. No new public surface. RLS is unchanged. Under (a) the DEFINER must not keep the claims after return (08 A21.4).
Alternatives considered: register the task with scope `platform`. Rejected: the job would run without tenant claims, dead letters would land in the platform-visible NULL-tenant rows (C0 02-TRD §7.4), and C6's per_tenant rule (C6 02-TRD:824) would be broken.
Tests that will prove it: T0B-10.C6_behaviour.test.sql:344-357. Add a fixture row in `core.g_task_registry` ('reporting.apply_provider_events', 'reporting', 'task', 'per_tenant', 10, true). A valid callback returns 1 and stores one graphile job whose payload tenant_id equals the token's tenant. Claims are empty after return. A token of tenant A cannot enqueue for tenant B.
