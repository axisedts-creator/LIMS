Title: CR-C0-T0B-12: lims_owner privilege to create the 08 §4.8 buckets in storage.buckets
From chunk: C0 (T0B-12)            To owner: C0-0B (05-SCHEMA §1 bootstrap) / C0-0A (SP-3 image facts)
Type: schema
Blocking? no for static gates (tests/db/T0B-12 61/61); yes for the live run of db/tests/storage/T0B-12_storage.test.sql.
Problem: db/migrations/20261105002200_storage__create_buckets.sql runs as lims_owner (CV §5.12: first statement SET LOCAL ROLE lims_owner).
  lims_owner is NOBYPASSRLS and 05-SCHEMA §1 grants it nothing in schema storage. In the Supabase image storage.buckets is owned by the
  Storage admin role with RLS enabled, so the INSERT will fail live (permission denied / RLS). Not verified (LD-51: no docker here).
Proposed change (exact, bootstrap 01_database.sql, superuser), pending SP-3 confirmation of the owner role name in the pinned image:
  GRANT USAGE ON SCHEMA storage TO lims_owner;
  GRANT SELECT, INSERT, UPDATE (public) ON storage.buckets TO lims_owner;
  plus either (a) an owner-only policy on storage.buckets TO lims_owner (needs the T0B-12 detector to allow policies TO lims_owner), or
  (b) a provisioning step that creates the buckets as the Storage admin role / via the Storage API with the service credential.
Backward compatible? yes.
Tenant/security impact: no end-user role gains access (REQ-SEC-034); lims_app/api/worker unchanged; storage.objects untouched.
Alternatives considered: SET ROLE to the Storage admin role from the migration (needs lims_migrator membership, broader than needed).
Tests that will prove it: bash db/tests/run-suites.sh db/tests/storage/T0B-12_storage.test.sql on a bootstrapped + migrated DB.
