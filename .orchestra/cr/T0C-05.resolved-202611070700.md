Title: CR-C0-0C-001: `engagement.booking.cancel` breaks the 08 §4.1 rule "staff codes never in patient sets"
From chunk: C0-0C            To owner: C16 (code owner; rule from 08 §4.1 / CR-C16-002)
Type: bug
Blocking? yes — T0C-05 (`codegen-fresh`, gen-permissions CI rule R3) cannot go green on the real contracts/permissions.yaml.
Problem: 08 §4.1 (08-CR-REGISTER.md:820) says "staff codes never to partner/patient sets … the one listed exception is `identity.self.manage` in `fixed_actor_permissions.partner.partner_member`". The same 08 §4.1 block (08:809, copied verbatim into contracts/permissions.yaml:26 and :181) puts `engagement.booking.cancel` (roles: [front_desk]) in `fixed_actor_permissions.patient`. C16 02-TRD §9 (line 710: "front_desk; patient"; E36 cancelMyBooking, S4 cancelBooking) uses one code for both. gen-permissions R3 therefore reports `R3 engagement.booking.cancel: staff code in a patient fixed set`; test "real contracts/permissions.yaml has no violations" (AC-0C-2.1) fails.
Proposed change (exact), pick one:
  (a) [recommended] 08 §4.1 exceptions list += "`engagement.booking.cancel` in `fixed_actor_permissions.patient` (patient self-cancel E36 and staff S4 share the code; centre scope applies to staff only)". C0-0C then adds it to PARTNER/PATIENT exceptions in tools/codegen/gen-permissions.ts.
  (b) C16 splits the code: staff S4 keeps `engagement.booking.cancel`; patient E36 gets a new roles: [] code named by C16, replacing it in the patient fixed set.
Backward compatible? (a) yes. (b) no — C16 E36 x-permission and C16 tests change.
Tenant/security impact: (a) none beyond today's data; (b) tightens separation of staff vs patient grants (REQ-SEC-072 spirit). No RLS/PHI change.
IRD/regulatory impact: n/a
Alternatives considered: silently exempt the code in the generator (rejected: invents an exception the spec does not list); drop it from the patient set (rejected: breaks C16 E36).
