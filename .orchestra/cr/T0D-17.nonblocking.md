Title: CR-C0-0D-T0D-17: Storage raw client shape + URL key, delete reason values, JPEG re-encode library
From chunk: C0-0D            To owner: C0-0C (03-IC §13.6) / C1 (Storage stack, SP-1)
Type: api
Blocking? no (T0D-17 unit tests pass against an injected raw client; live.test.ts is gated and not run, LD-51)
Problem:
1. 03-IC §13.6 / 02-TRD §11 name no config key for the Storage service URL and the storage-api HTTP shape is UNVERIFIED (C1 02-TRD §8.2 row core_storage_service_key). The adapter therefore requires an injected `connect(credential, url)`; with none it fails closed at boot. The test option name `url` is the tester's assumption.
2. `ctx.storage.delete(bucket, objectPath)` has no reason argument, but `lims_core_storage_deletes_total{bucket,reason}` needs one; P-12 lists three cases (E-class, retention elapsed, anonymisation) without coded values. Interim: fixed `reason="unspecified"` [CONV].
3. images.reencode for image/jpeg needs a decoder; no image library is pinned for services/api. Interim: JPEG with images.reencode -> 422 common.upload_quarantined (fail closed); PNG re-encoded with node:zlib only.
Proposed change (exact): (1) add config key `LIMS_CORE_STORAGE_URL` [proposed name] + pin the storage-api endpoints after SP-1; (2) `delete(bucket, objectPath, opts?: { reason: 'e_class' | 'retention_elapsed' | 'anonymisation' })` [proposed values]; (3) pin an image library (e.g. sharp, already in the pnpm store via another package) in the C0-0A dependency table.
Backward compatible? yes (all additive / optional)
Tenant/security impact: none new; credential still read only from LIMS_CORE_STORAGE_KEY_FILE by core/storage/**.
Alternatives considered: guessing the Supabase storage-api REST shape (rejected: vendor API not in spec); a free-text reason (rejected: unbounded label cardinality).
Tests that will prove it: live.test.ts with LIMS_TEST_STORAGE_URL set; a delete-reason matrix test; a JPEG fixture re-encode test.
