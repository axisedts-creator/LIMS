Title: CR-C0-0D-PARTYSET-1: contract gaps found building the T0D-PARTYSET-1 party settings, onboarding queue, doctor and penalty screens
From chunk: C0 (lane C0-0D, task T0D-PARTYSET-1)            To owner: C0-0B (contracts/openapi/partners.yaml, catalog.yaml)
Type: api
Blocking? no. T0D-PARTYSET-1 ships with the limits below. The server already enforces every rule; the gaps only limit what the screens can show before a request.

Problem (what cannot be done today):
(a) PartyOnboarding (partners.yaml components.schemas.PartyOnboarding, read by listPartyOnboarding) has no creator field. done_when 3 asks for Approve, Hold and Reject to be disabled with a visible reason for the person who created the record, and for a Requested By column. The service enforces the creator rule (service/partyset.service.ts:175, 403), but the web (apps/web/src/features/partners/components/OnboardingQueue.tsx) can only show the reason after the server refuses, and Requested By cannot be filled.
(b) NonComplianceEvent (partners.yaml components.schemas.NonComplianceEvent, read by listNonComplianceEvents) has no `party_name` or `penalty_name`. The Penalty Events list (apps/web/src/features/partners/components/PenaltyEvents.tsx) joins names from listNonCompliancePenalties and the party lists, each capped at one page of 200 rows; names past the first page show as the id.
(c) Doctor (catalog.yaml components.schemas.Doctor, DoctorUpdate) has no `tax_number` (doctor PAN). done_when 4 asks for PAN and national id numbers masked with a Show button; only national_id_number exists for doctors, so done_when 4 is met in part (partners carry tax_number already).
(e) No party search operation. The Raise dialog of Penalty Events needs a party picker across party_kind partner, credit_party, doctor and referrer; today it reads the first page of each list (listPartners, listCreditParties) with no name filter.

Proposed change (exact, all additive):
(a) Add optional `created_by: Uuid` and `created_by_name: string (minLength 1, maxLength 200)` to PartyOnboarding. The handler fills them from the actor that queued the row. The web disables the decision buttons when created_by equals the current membership and shows created_by_name under Requested By.
(b) Add optional `party_name: string (minLength 1, maxLength 200)` and `penalty_name: string (minLength 1, maxLength 120)` to NonComplianceEvent, filled by the handler join (same lengths as PartyOnboarding.party_name and NonCompliancePenalty.name).
(c) Add optional `tax_number` to Doctor (masked like national_id_number, full value only through the existing reveal path with partners.party_id_number.read and an audit line, LD-321) and to DoctorUpdate (nullable, unset like national_id_number).
(e) Add `GET /v1/partners/admin/party-search` (operationId searchParties, x-permission partners.penalty.manage, x-context tenant, x-idempotency none, paged with cursor, query `q` minLength 2 maxLength 100, optional `party_kind`). Rows: `{ party_kind, party_id, party_name }`. Name, path and permission are proposals for the owner to confirm.
Backward compatible? yes. Every item adds an optional response field, an optional request field, or a new read operation.
Tenant/security impact: no new PHI. Same RLS as the existing partners and catalog tables. (c) keeps the LD-321 masking and audited reveal; the full doctor PAN never appears in a list or read response. (e) returns names only, tenant scoped, behind an existing permission.
IRD/regulatory impact: none. (c) stores a PAN already captured for partners; retention of PAN and national id numbers stays a founder confirmation (LD-321 founder steps).
Alternatives considered: (a) keep refusing with 403 only. Accepted for now: the server rule holds and the screen shows the reason after the refusal. (b) keep the client-side join. Accepted for now with the 200-row ceiling. (c) store doctor PAN in a free note. Rejected: it would bypass masking and the audited reveal. (e) page through every list. Rejected: N requests per open on large tenants.
Tests that will prove it: (a) partyset1.onboarding.test.tsx: Approve, Hold and Reject are disabled with the creator reason before any request when created_by is the current user, and Requested By shows created_by_name. (b) partyset1.penalties.test.tsx: event rows show party_name and penalty_name from the row with no list join. (c) partyset1.idnumbers.test.tsx: the doctor form shows a masked PAN with a Show button that needs partners.party_id_number.read. (e) the Raise picker calls searchParties once per query. Each is paired with a T0C contract test and a T0B handler test.
