Title: CR-C2-T14: (1) role description maxLength 500 (contract) vs 300 (DB CHECK); (2) batched GoTrue sign-out job_key/payload for role-change fan-out
From chunk: C2            To owner: (1) C0-0C (contracts/openapi/identity.yaml) or C0-0B (db roles__text__ck); (2) C2 doc owner / founder (C2 02-TRD §10 task row)
Type: api (1), port/job (2)
Blocking? no — T14 ships with 300 and the batch key below marked [CONV]; the future `identity.gotrue_signout` task must be built to whatever this CR settles.

Problem:
(1) contracts/openapi/identity.yaml:5584/5598 (RoleCreateRequest/RoleUpdateRequest/Role `description.maxLength: 500`) and C2 02-TRD §5.4 createRole (`≤500`) contradict DB `roles__text__ck` (C0 05-SCHEMA:772, max 300). A 301–500 char description passes contract validation and then fails the CHECK as a 500. Serves AC-B2.1/AC-B2.3. T14 enforces 300 (role.service.ts DESCRIPTION_MAX).
(2) C2 02-TRD §10 (line 533) fixes `job_key = signout:<session_id or user_id>:<reason>` with a single-user `adminSignOutUser(userId)` task, but 03-APP-FLOW §4.3 / §9.2 require role-change fan-out in batches of 200 (AC-B2.4). One job per user breaks the batching rule; one job per batch has no spec'd key/payload.

Proposed change (exact):
(1) Option A (preferred, safe side): identity.yaml RoleCreateRequest/RoleUpdateRequest/Role `description.maxLength: 300`; 02-TRD §5.4 createRole `≤300`. Option B: C0-0B widens `roles__text__ck` to 500 and T14 sets DESCRIPTION_MAX = 500.
(2) Add to C2 02-TRD §10 `identity.gotrue_signout` row a batch form: job_key `signout:<role_id>.<role_version>.<batch_index>:role_change`, payload `{ tenant_id: uuid, user_ids: uuid[] (1..200), reason: 'role_change' }`; task calls `adminSignOutUser` per user_id. Single-user form unchanged.

Backward compatible? (1A) narrows an unreleased contract field — no consumer has shipped against it; (1B) additive. (2) additive (new payload shape for a task not yet implemented).
Tenant/security impact: none new. No RLS change, no PHI. Payload carries tenant_id; task runs with that tenant's system ctx. Sessions are already revoked in the request tx (SS9); the job only clears GoTrue refresh tokens.
Alternatives considered: (1) keep 500 and let the CHECK fail (rejected: 500 error for valid contract input). (2) one job per user with the existing key (rejected: violates §4.3 batches of 200, thousands of jobs per role edit).
Tests that will prove it: (1) role.service.test.ts description-length cases at the agreed max + contract test on identity.yaml. (2) worker test for `identity.gotrue_signout` consuming the batch payload; T14 tests already assert key/payload shape and 200-batch split.
