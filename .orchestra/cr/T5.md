Title: CR-C2-021: lims_app read path for support-session platform staff display name
From chunk: C2            To owner: C0-0B
Type: schema
Blocking? no  (T5 ships with staffDisplayName = '' when the row is unreadable; session validity depends only on identity.support_sessions)
Problem (what you cannot do today, with the user story / acceptance criterion it serves):
  02-TRD §7.1 asks getActor for a support actor to carry the "platform staff display name". identity.platform_staff has FORCE RLS and its only SELECT policy is
  `platform_staff__select__owner_only TO lims_owner` (db/policies/identity.sql:129), so the IdentityPort repo (runs as lims_app) cannot read display_name.
  T5 review item 1: an INNER JOIN made every support actor fail with identity.support_session_required (C2-1, §7.2 7(c)). Fixed with LEFT JOIN + coalesce(..., '').
Proposed change (exact) — pick one:
  A) Resolver puts the display name in the JWT claims (support_staff_display_name) when the support session is minted; repo reads it from request.jwt.claims.
  B) SECURITY DEFINER fn identity.support_session_staff_display_name(p_tenant_id uuid, p_support_session_id uuid) RETURNS text, owner lims_owner,
     returns ps.display_name only when an identity.support_sessions row with that id exists for p_tenant_id; GRANT EXECUTE TO lims_app.
Backward compatible? yes
Tenant/security impact: B adds a narrow DEFINER read of one non-PHI column of platform staff, keyed by a tenant-scoped session id; no new public surface.
IRD/regulatory impact: none
Alternatives considered: SELECT policy on platform_staff for lims_app (rejected: exposes all staff rows/emails to every tenant request).
Tests that will prove it: IdentityPort.live.test.ts support-actor case asserts staffDisplayName = 'Support T5' (in addition to the allowlist profile).
