Title: CR-C2-T7-a: pre-auth read/write paths for the MFA operations (platform sessions/factors/platform_events, session token + e-mail read)
From chunk: C2            To owner: C2 (schema, 05-SCHEMA §4.1/§4.2/§4.10, 08 A28.1)
Type: schema
Blocking? no for T7 unit/integration tests (in-memory store); yes for live-DB platform MFA (verifyMfaChallenge / startMfaEnrolment / completeMfaEnrolment for kind=platform)
Problem (AC-A2.2, AC-A3.2, D-215):
 1. app.identity_session_by_token returns no access/refresh token, aal, mfa_failed_attempts, expiry or e-mail. repository/mfa.repo.ts loadSession
    therefore SELECTs identity.sessions (+ core.users / identity.platform_staff for the e-mail) FOR UPDATE. Tenant rows pass sessions__select__tenant
    after bindTenant; platform rows (tenant_id NULL) have no lims_app SELECT policy pre-auth (sessions__select__platform needs is_platform_actor,
    __owner_only needs lims_owner), and identity.platform_staff is lims_owner-only.
 2. identity.mfa_factors SELECT for a tenant-less factor pre-auth: same gap (mfa_factors__select__platform needs is_platform_actor).
 3. identity.platform_events INSERT of platform_mfa_enrolled (D-215) pre-auth: only platform_events__insert__owner_only (bootstrap_admin_created).
 4. No auth event type for "enrolment started" (none written); unspecified: no verified factor while mfa_pending (handler: 409), 5-failure revoke of a
    voluntary (active) enrolment (handler: revokes, same as login), login_succeeded on voluntary enrolment (handler: not written).
Proposed change (exact): one SECURITY DEFINER app.identity_mfa_session_context(p_token_sha256 bytea) RETURNS (session_id, kind, state, tenant_id,
    user_id, membership_id, platform_staff_id, aal, access_token_enc, refresh_token_enc, enc_key_id, mfa_failed_attempts, access_expires_at,
    idle_expires_at, absolute_expires_at, email_normalized) ... FOR UPDATE; app.identity_platform_auth_write_mfa_factor extended with a read mode
    (or app.identity_platform_mfa_factors(p_user_id)); app.identity_platform_auth_write_platform_event(p_user_id, p_row jsonb) allowlisting
    event_type = 'platform_mfa_enrolled'. mfa.repo.ts then swaps the SQL behind the same MfaRepo methods (handlers unchanged).
Backward compatible? yes (additive)
Tenant/security impact: new DEFINERs, search_path='', owner-only, keyed by token hash / user id (AU-T21, D-212). No new public surface.
Alternatives considered: run platform MFA under a platform actor claim (not available pre-auth).
Tests that will prove it: db/tests/identity pgTAP for each DEFINER; a live repo test of mfa.repo.ts for both kinds.
