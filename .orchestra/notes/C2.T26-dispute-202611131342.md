# C2.T26 dispute (writer) — 5 tests are wrong; implementation not changed for them

## 1. t26.tenants.test.tsx "PL-3 Tenant detail — Overview and lifecycle": `open()` wipes the route the test just registered (4 tests)
`open()` calls `resetApi(perms)`, and `resetApi` deletes every key of `routes`. The tests register the POST route BEFORE `open()`:
`routes[POST …/activate] = …; await open('provisioning');` → the POST is answered by the harness fallback `503 common.dependency_unavailable`.
Affected: "Activate → … success refreshes", "409 identity.tenant_not_ready …", "409 common.version_conflict …", "403 auth.mfa_required …".
(The Suspend / Reactivate / Terminate tests pass only because they assert the request, not the response handling.)
Evidence: debug log in the action caller showed `{"ok":false,"status":503,"code":"common.dependency_unavailable"}` for the activate POST.
Proof the UI is right: a temporary scratch copy of the 4 cases with the route registered after `resetApi` passed 4/4 (scratch file deleted).
Fix: in `open()`, register routes after `resetApi`, e.g. `const open = async (status, perms = SUPER, extra = {}) => { resetApi(perms); Object.assign(routes, extra); … }`,
or keep the routes across the reset (`const saved = { ...routes }; resetApi(perms); Object.assign(routes, saved);`).

## 2. t26.tenants.test.tsx PL-2 "rejects the tenant code "x"×33 …" contradicts the maxLength test
The same file requires `maxLength === 32` on the Tenant code input (test "single page with sections…"). user-event respects `maxLength`,
so typing 33 × "x" leaves 32 × "x" in the field — a VALID code under `^[a-z][a-z0-9_]{2,31}$` (1 + 31 chars). The form correctly submits it.
A 33-character code cannot be entered, so this case cannot fail validation. Fix: drop the 33-char case, or assert the field value is truncated to 32
(`expect(input.value).toHaveLength(32)`) instead of "no POST".
