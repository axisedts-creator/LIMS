CHANGES

1. services/api/src/modules/lab/service/cache.ts:66 together with services/worker/src/jobs/lab/consumers/catalog.changed.v1.ts:14. Invalidation never reaches the API cache. The worker is its own process (services/worker/src/main.ts `startWorker`), so `getCatalogCache().invalidate(...)` in the consumer only clears the worker's singleton. The API process cache that `withCatalogCache` fills is never invalidated, so after a catalog change it keeps serving stale `referenceRangeFor` / `criticalLimitsFor` / `mapInstrumentCode` results for as long as the process runs. That is a result-safety defect.
   Fix: make the API cache safe without a signal from another process, as 02-TRD §6.2 (CatalogPort row) requires: the key is `(tenant, method, input, catalogRevision)`. Before each lookup in `withCatalogCache`, read the tenant's current catalog revision with a cheap read (for example the C3 catalog-state revision the C3 cache already keys on, `modules/catalog/cache/catalogCache.ts:1-2`) and put it in the key. Keep the worker's `invalidate` call as eviction only. Add a test where a fill happens at revision N, the revision moves to N+1 with no `invalidate` in that process, and the next read is a miss.

2. services/api/src/modules/lab/service/cache.ts:90. `Number.isInteger(rev) ? rev : 0`: only `resolveOrderables` returns `catalogRevision` (catalog/ports/CatalogPort.impl.ts:324). The other 6 cached methods (`getTest`, `referenceRangeFor`, `criticalLimitsFor`, `mapInstrumentCode`, `resolveCommentCodes`, `getReferrer`) are stored at revision 0. In a process that has had any invalidation (floor ≥ 0), every later `set` for these methods is dropped, so they are never cached. In a process that never gets an invalidation (the API, see item 1), they are cached forever.
   Fix: take the revision from the per-request revision read in item 1, not from the result body. Add a test that covers a port method whose result has no `catalogRevision`.
