Fix: register `'reporting.release_if_eligible'` in `manifest.tasks` as a no-op stub that only logs, with `maxAttempts` 10 (02-TRD §9 row), plus a `[CONV]` comment saying the real task replaces it in its own task. Also add a manifest test asserting that every identifier the task enqueues (`reporting.render_report_version`, `reporting.release_if_eligible`) is present in `manifest.tasks`.

2. `services/worker/src/jobs/reporting/tasks/render_report_version.ts:65-104`: the `try` wraps SQL statements: the template SELECT, the `input_files` SELECT, the `rendered` UPDATE (CHECK constraints `report_versions__path__ck` / `__pdf_present__ck` / `__hashes__ck`) and the enqueue at line 98. If any of them errors, Postgres aborts the transaction. On the final attempt, or for a Permanent error, `fail()` at line 104 then runs inside that aborted transaction and fails with "current transaction is aborted". In that case `render_failed` is never committed, the metric and alert never fire, and the version stays `rendering`, which `sweep_stuck_renders` re-enqueues forever. That breaks AC-03.9 and E11. Fix: run `SAVEPOINT render_attempt` right after the status check (before line 65). In the `catch`, run `ROLLBACK TO SAVEPOINT render_attempt` before `await fail(...)`. On the non-final throw path the outer rollback still applies. Add a test where the fake tx rejects the `rendered` UPDATE (or the enqueue) on the final attempt, and assert that the savepoint rollback is issued before the `render_failed` UPDATE.
