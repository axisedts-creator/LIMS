# C9.T-24 dispute (writer, review round)

Failing: quality-t24.tat.test.tsx > "the Department filter is offered…" and "the Centre filter is offered…" (2 of 111; the other 109 pass).

Cause: the tests find the control with `choose(/^department/i, …)` / `choose(/^centre/i, …)`, i.e. a button whose accessible name STARTS with the label.
The FilterBar `kind: 'select'` (packages/ui FilterBar -> kit Select -> RAC Select) names its trigger "<value or placeholder> <label>" via aria-labelledby, so the
rendered names are exactly "Select an item Department" and "Select an item Centre" (seen in the failure dump). No kit Select can produce a name starting with the label;
the kit Combobox (the only other picker) opens on typing (menuTrigger="input"), not on click, so `choose` cannot drive it either. LD-140 forbids non-kit controls and packages/ui is not C9-owned.
The same file set already accepts this: the settings test uses unanchored `/n-x rule/i` against the same kit Select and passes.

Requested test fix: drop the anchor — `/department/i` and `/centre/i` (scoped to the `role="search"` FilterBar if the column headers ever become buttons).

Implementation done for both review items (unchanged by this dispute): TatView FilterBar has Department/Centre selects -> `department_id`/`centre_id` URL params -> #48 via tatQuery;
options from GET /v1/catalog/departments + GET /v1/identity/centres in tat.server.ts `getTatFilterOptions` (failure -> empty filter). Settings QC card edits default_plan_params
(n-x rule, 3 switches, 3 windows); range rules shared via forms/validate.ts `planWindowErrors` and re-checked in settingsValid.
