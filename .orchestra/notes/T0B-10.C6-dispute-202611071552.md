Live run `bash db/tests/run-suites.sh db/tests/reporting/T0B-10.C6_{schema,behaviour}.test.sql` (supabase/postgres 17.6.1.136, graphile-worker installed): migrations and seeds load cleanly; the suites fail on the points below. The writer's scratch copy with fix 1 applied and debug rows added is in `build/c6gen/tap/` (gitignored); its output is in `build/c6gen/live2.txt` and `live3.txt`.

1. behaviour.test.sql:94 — the reports fixture passes `'order_id', r.o, 'patient_id', r.p` as bare ints (11, 1). This aborts the file with `invalid input syntax for type uuid: "11"`. Line 99 shows the intended form: `pg_temp.uid(r.o)` / `pg_temp.uid(r.p)`. With that fixed, the file runs to the end.
2. schema.test.sql:65-67 (tests 243/244) — these checks do not exclude `event_inbox`. C0 owns `reporting.event_inbox` and creates `event_inbox__delete__owner_only` on it (C0 05-SCHEMA:1224/1226), so the DELETE table list gets an extra `event_inbox` entry and the policy name does not match `__tenant_expired`. This is the same scope error as the C5 ruling, item 1. Fix: add `AND p.tablename <> 'event_inbox'`.
3. schema.test.sql:103-104 (tests 676-697) — lims_api and lims_worker are members of lims_app with INHERIT TRUE (db/bootstrap/00_roles.sql:26-27). C6 05-SCHEMA §6.3 grants lims_app DELETE on the four E tables, so `has_table_privilege('lims_api'|'lims_worker', <E table>, 'DELETE')` returns true. Policies restrict DELETE to the system purge. Fix: exclude the 4 E tables for lims_api/lims_worker, or test only roles that do not inherit lims_app.
4. schema.test.sql:113-114 (tests 798/814/830) — same inheritance: lims_api gets SELECT on the v_pub_* views through lims_app (§7 grants it to lims_app). Fix: expected value `r IN ('lims_app','lims_analytics','lims_api') AND p = 'SELECT'`, or drop lims_api from the role list.
5. behaviour.test.sql:148, 151 (tests 19-24, 71) — the C0 helpers `app.current_partner_id()` / `app.engagement_patient_ids()` read `partners.partner_users` / `engagement.account_patient_links`. Those are Wave-2 tables and do not exist yet. For partner/patient actors the spec-verbatim policies therefore raise `42P01 relation ... does not exist` instead of returning 0 rows. That still fails closed, but it is not `n=0`. The spec ran its own check with these helpers stubbed (§6.2 note). Fix: either stub the two helpers (or create the two tables) inside the test transaction, or accept an `E42P01` result as a denial until Wave 2.
6. behaviour.test.sql:344-357 (tests 272-275, 281-282) — `app.reporting_ingest_provider_callback` (§6.2 verbatim) fails with `P0001 unknown_task_identifier`, because `reporting.apply_provider_events` is not in `core.g_task_registry`, so `app.enqueue_job` rejects it. Tests 281/282 cascade from this: no row was inserted, so the UPDATE matches 0 rows. Registering the task is a seed / registry matter outside this task's files (db/migrations/*_reporting__*, db/policies/reporting.sql, db/meta/tables.yaml). Note also: if the task is registered with scope `per_tenant`, the wrapper's tenant-claims check would then reject this pre-tenant call (`job_tenant_mismatch`, queue wrapper:20-23). The arbiter should decide which scope applies, or whether a CR is needed. Until then the test needs a fixture row in `core.g_task_registry`, or the test should be scoped out like T0B-05.

No DDL change requested. Everything in the migration is C6 05-SCHEMA §6/§6.1/§6.2/§7, either verbatim or expanded from its own templates.
