# WEB-T04 dispute — `flag_map` is JSON object TEXT in the contract, the tests use an object
**Claim:** the WEB-T04 tests send/expect `flag_map` as a JS object; contracts/openapi/catalog.yaml (`InstrumentCodeMap`, `InstrumentCodeMapCreate`, `InstrumentCodeMapUpdate`, `InstrumentCodeMapRow`) types it `type: string, maxLength: 2000` ("JSON object text [CONV]"). The API (C3, API-T14) enforces this: `services/api/src/modules/catalog/__tests__/integration/instrumentMaps.service.test.ts:198` rejects `{ flag_map: { H: 'HIGH' } }` ("flag_map as an object (the DTO is text)") and `:57-62` shows the DTO returns `typeof flag_map === 'string'`.
**Effect:** an impl that makes these tests pass forwards an object to C3 → every create/edit/copy with a flag map gets `400 common.validation_failed` in production; the list DTO's `flag_map` (a string) would also not be countable as an object.
**Affected tests (apps/web/src/features/instruments/__tests__/):**
- `web-t04.server.test.ts`: L165-170 (create carries `flag_map: {H,L}`), L178-183 (20-entry boundary object), L214-221 (flag_map limits: 21 entries / key>16 / value>64 / array / non-string value — all expressed on objects), L244-255 (PATCH with `flag_map: {H:'HIGH'}`), L310 (bulk-upsert row `flag_map: {H:'HIGH'}`).
- `web-t04.components.test.tsx`: fixture `cm()` L75 and `MAPROWS` carry `flag_map` as an object ("Flag map count" 2 is read from it, L181).
**Proposed fix (tester):** BFF fns accept `flag_map` as JSON object text (string ≤ 2000 chars, parsed ≤ 20 entries, key ≤ 16, value ≤ 64, values strings, not array/null/scalar) and forward the string unchanged; the same limits apply to the string's parsed form; `unset: ['flag_map']` unchanged. Fixtures use `JSON.stringify({H:'HIGH',L:'LOW'})`; the component parses it for the count and builds it from the KeyValueListEditor rows. Alternatively the tester may rule that the BFF takes an object and serialises it (`JSON.stringify`) — then the assertions on the outgoing body must expect the string.
**Status:** no WEB-T04 implementation files written; stopped per the writer rules. Everything else in the tests (names, props, permission gate, errors, idempotency) is implementable as assumed.
