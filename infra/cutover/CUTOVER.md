# CUTOVER: build the ONE Nepal staging server

Audience: one human at a terminal. Target: single host `staging-1`, inventory `infra/ansible/inventories/staging-lean` (topology_profile `lean`, groups `data`+`app`+`ops`, `dr: {}`, `backup: {}`), `LIMS_ENV=staging`. Source: CR `.orchestra/cr/NEPAL-single-host.md`, status `infra/cutover/STATUS.md`, server checks `infra/cutover/SERVER-TESTS.md`.

**This host is STAGING with SYNTHETIC DATA ONLY.** It never holds PHI (04 S1 needs >= 2 VMs plus a third Nepal location; one box cannot meet it). No real patients, no real tenants, no live payment keys, no C18 import. Promotion to prod needs `backup-1` at a second site (B12) and a restore drill under 35 days old (04 I3). See section 6: today the answer is NO-GO for any real data.

Notation: `MANUAL:` = the kit has no command for this step; do what it says. Every other command exists in the repo. Placeholders (`example.invalid`, `203.0.113.x`, `<repo-url>`) are fake: replace them on the server, never in the repo. Run everything from the repo root unless stated.

## QUICKSTART

Fresh Ubuntu 24.04 LTS, as a sudo user, five commands:

```bash
git clone --branch claude/nepal-migration-agent-25hkhg <repo-url> lims && cd lims      # (a)
sudo bash infra/cutover/bootstrap.sh --dry-run                                          # (b) prints the plan, changes nothing
sudo bash infra/cutover/bootstrap.sh                                                    # (c) builds the host
sudo LIMS_ENV=staging bash infra/cutover/server-smoke.sh                                # (d) server-only checks, exit code = number of FAILs
sudo bash infra/cutover/bootstrap.sh --rollback                                         # (e) undo
```

`bootstrap.sh` asks all human inputs once at the start (domain, TLS e-mail, age key custody). Section 2 below stays as the manual, explicit equivalent of what `bootstrap.sh` automates; use it to understand, resume or debug a step.

**bootstrap.sh will pause for these MANUAL steps** (it prints the exact text and waits; with `LIMS_BOOTSTRAP_NONINTERACTIVE=1` it exits 3, you do the step and re-run, done steps are skipped):

1. Install SOPS 3.13.3 (step 3): it is not an Ubuntu package; download the pinned release, verify its sha256, put it in `/usr/local/bin/sops`. No checksum is recorded in the repo: take it from the upstream release checksums file and give it as `LIMS_SOPS_SHA256` (+ `LIMS_SOPS_URL` or `LIMS_SOPS_FILE`) so bootstrap verifies and installs it.
2. Age key custody (step 5): the private key exists only on this server; name who keeps an offline copy.
3. Build and push the images, then write the `lims_runtime_images` file (step 8): `infra/ci/build.sh`, `infra/ci/push.sh staging ...` (writes `staging.lock.yaml`), `push.sh mirror` for third-party images; `infra/ci/runtime-images.sh` converts the lock to the `lims_runtime_images` file (bootstrap step 8 runs it); bootstrap also builds the derived DB image there.
4. `site.yml` fails closed the first time (step 7): the last play (`lims_runtime : Preconditions`) needs image digests, and the registry that receives them is created by that same run. bootstrap.sh treats exactly that stop as partial, pauses at step 3 above, then re-runs `site.yml` (step 9).
