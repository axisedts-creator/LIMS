`internal: true` Docker networks have no external route (documented Docker behaviour; AC-09.1 tests it). Host-level `DOCKER-USER` nftables rules (§5.5) add the per-network allowlists above. A container attached to several networks gets its default route from a non-internal one; for api/worker that is `edge_net` or `db_net`, both of which `DOCKER-USER` restricts, so their only internet path is Squid on `app_net` (`LIMS_CORE_EGRESS_PROXY_URL`). Rules that filter traffic **between two containers on the same bridge** (the `edge_net` "only to/from nginx" rule and the `render_net` "sandbox only from the workers" rule) see bridged packets only when `br_netfilter` is loaded with `net.bridge.bridge-nf-call-iptables = 1`; the `docker_engine` role sets both and T-14 proves it with `egress_probe.sh` (UNVERIFIED until then; if it does not hold, the sandbox's worker-only rule rests on its bearer token alone and T-14 records this in `DECISION.md`).

### 5.5 Firewall (nftables, role `nftables`)
- `inet filter input`: policy drop; allow established/related, loopback, ICMP echo rate-limited (10/s), `udp dport 51820 ip saddr @wg_peers`, on app-1 `tcp dport {80,443}`; on `wg0` interface allow only the §3.3 wg ports from the expected source hosts (e.g. 5432 on data-1 only from the app-1 and dr-1 wg IPs — ops-1 never connects to the application DB: migrations run as a one-shot container on app-1, §7.9; postgres_exporter runs on data-1; 6432 only from app-1; metrics ports only from ops-1).
- `inet filter forward` + `DOCKER-USER` (iptables-nft compatibility table Docker uses), in this order (08 A25 D-203):
  1. accept `ct state established,related`;
  2. public interface → only the nginx container (`172.30.10.10`) on 80/443; anything else from the public interface is dropped;
  3. `wg0` → published metrics ports of api-a/b and worker-a/b (§3.3) only from the ops-1 wg IP;
  4. `edge_net` (`172.30.10.0/24`): accept only packets whose source or destination is the nginx container; drop the rest (no egress for web/portal/partner/api over `edge_net`);
  5. `db_net` (`172.30.50.0/24`): accept new connections to `{{ db_primary_wg_ip }}` (data-1 wg IP; dr-1 wg IP after promotion) on tcp 5432/6432; accept from the `auth` container (`172.30.50.20`) to the IPs of `smtp_relay_fqdn` on tcp 587 only (set `@smtp_relay_ips`, resolved by the `egress_proxy` role at deploy and refreshed hourly [CONV]; listed in `egress-allowlist.yaml` with owner C2/C1, REQ-ARCH-018, and in the F-01 register — Squid cannot proxy SMTP, D-203 (3)); drop the rest;
  6. `render_net` (`172.30.40.0/24`): drop everything leaving the subnet; inside it, drop new connections to the pdf-sandbox IP from any source other than worker-a/b (needs `br_netfilter`, §3.2);
  7. `app_net`/`auth_net` are `internal` (no route); defence in depth: drop anything leaving their subnets;
  8. `egress_net`: only the Squid container may forward to the internet, tcp 443 (+ 80 for package mirrors that are listed as such) — Squid itself enforces the FQDN allowlist.
- `output` on product hosts (data-1, app-1, dr-1): policy accept only to `wg0` peers, DNS resolver (provider resolver IP in inventory), and — app-1 only — the ACME CA endpoints (resolved by the `acme` role at renewal time). Container egress is governed by the forward rules above. Everything else from product hosts goes through ops-1 Squid (apt) or is blocked. Every egress destination (Squid FQDNs, the GoTrue SMTP relay, the ACME CA) is listed in `infra/edge/egress-allowlist.yaml` with owner chunk, purpose, 04 §11 row and F-01 status; empty for any destination not approved (B11). ### 6.6 Proxy behaviour (`snippets/proxy.conf`)
- `proxy_set_header X-Forwarded-For $remote_addr;` (overwrite — single trusted hop; matches C0 `LIMS_CORE_TRUSTED_PROXY_HOPS=1`), `X-Forwarded-Proto https`, `Host $host`, `X-Edge-Request-Id $request_id` (nginx hex id for log correlation; the canonical UUIDv7 `request_id` is generated by BFF/API — CV §9.1).
- Client IP (08 A25 P-61, A13 D-32, A19 P-45): on staff_web, partner **and portal** the BFF forwards this `X-Forwarded-For` value to the API together with its own `X-Lims-Bff-Key` (kinds `staff_web`, `partner`, `portal`; secrets §8.2). For public api-origin routes (bridge agent, mobile/patient sessions, callbacks, payments) the API's TCP peer is nginx; C1 sets `LIMS_CORE_TRUSTED_PROXY_CIDRS=172.30.10.10/32` (the nginx container on `edge_net`, §3.2) on api-a/b so the core takes `X-Forwarded-For` from nginx only. Requests from any other peer without a valid BFF key use the peer address. Module code reads only `ctx.clientIp`.
- Strip inbound internal headers: `proxy_set_header X-Request-Id "";` `proxy_set_header X-Forwarded-Host "";` and any `X-Lims-*` (map-based clear) — with one exception (08 A25 D-206): **`X-Lims-Background` passes through unchanged on the BFF origins staff_web, partner and portal** (the browser's `@lims/ui` polling/SSE helpers set it; the BFF maps it to `resolveSession` with `touch: false`, so it can only *reduce* session touching and spoofing it only shortens the sender's own session). On the api origin it is stripped like every other `X-Lims-*` header.
- Timeouts [CONV]: `client_header_timeout 15s; client_body_timeout 15s; send_timeout 30s; keepalive_timeout 30s; proxy_connect_timeout 5s; proxy_read_timeout 60s` (staff_web 300 s for SSE; the BFF sends `X-Accel-Buffering: no` on SSE responses, which nginx honours, so no per-path buffering config is needed).

### 6.7 Access logs (`snippets/logformat.conf`)
JSON lines: `ts, edge_request_id, remote_addr, host, method, route, status, bytes, req_time, upstream_time, upstream_status, ua_class, limit_req_status`. `route` is computed by a `map $uri $route` that rewrites:
- `~^/r/[^/]+` → `/r/{token}` and `~^/v/[^/]+` → `/v/{token}` (portal; incl. `/r/payments/{id}/done`, 08 A11.1);
- `~^/v1/reporting/provider-callbacks/[^/]+` → `/v1/reporting/provider-callbacks/{token}` (CR-C6-013: the token segment is never written; C6 CB1/CB2);
- `~^/v1/payments/launch/[^/]+$` → `/v1/payments/launch/:token`; `~^/v1/payments/callbacks/esewa/[^/]+/(success|failure)$` → `/v1/payments/callbacks/esewa/:token/$1`; `~^/v1/payments/callbacks/khalti/[^/]+$` → `/v1/payments/callbacks/khalti/:token` (CR-C15-008 item 3, its `:token` spelling); any other `/v1/payments/callbacks/…` path → `/v1/payments/callbacks/{unmatched}`;
- `/auth/confirm` → `/auth/confirm`.

**`$args`/`$request_uri` are never logged** on any route (tokens, Khalti `mobile` on payment callbacks — IC §7, CR-C2-012, CR-C15-008, 04 A14). User agent is reduced to a class (`browser|bridge-agent|bot|other`) [CONV] to avoid fingerprint storage. Logs go to `/var/log/nginx/access.json` (rotated daily, 14 files) and are shipped by Fluent Bit (§10).

## 7. Self-hosted Supabase and LIMS runtime

### 7.1 Upstream vendoring
`infra/compose/supabase/upstream/` is a byte-for-byte copy of one upstream `docker/` commit (compose files + `volumes/` config). `UPSTREAM.lock` records repo, commit, date and sha256 of every file; CI fails if a file differs from the lock. Upgrades = new snapshot, full staging soak, then prod ("tested set", REQ-ARCH-012). Never mix image tags from different snapshots. All C1 changes live in override files. `UPSTREAM.lock` is the **single source of Supabase image digests** (08 A25 D-208): C0's dev stack (`tools/devstack/compose.yaml`) reads them from it (C1 keeps ownership; 01-CM §3 note), a C0-0A CI job wired per P-14 fails when the digests differ, and C0's SP-1 records the lock commit it ran against. A snapshot bump is therefore one C1 PR that also triggers C0's dev-stack check.

### 9.4 RPO ≤ 15 min (04 I2) — parameters and arithmetic (08 A25 D-205, one set everywhere)
- `archive_timeout = 60s` (`archive_timeout_s: 60`): with any write activity a segment is switched at least every 60 s; `archive-async` pushes queued segments continuously to both repos; the 15-min `check` forces a switch and confirms arrival.
- Metric `lims_ops_wal_repo2_newest_age_seconds` = now − time of the newest WAL segment in repo2: `pgbackrest_metrics.sh` (every minute) reads the archive max of repo2 from `pgbackrest info --output=json` and that segment's modification time from `pgbackrest repo-ls --repo=2 --output=json` (command/option names verified in T-09). It is **not** measured from the `check` completion time. On an idle database `archive_timeout` switches nothing, so between two 15-min `check` runs the age can approach 900 s without any data at risk; the script therefore also exports `lims_ops_wal_unarchived_bytes` = `pg_wal_lsn_diff(pg_current_wal_lsn(), <end LSN of pg_stat_archiver.last_archived_wal>)` (the segment name is converted to its end LSN in the script) [CONV], and the two age alerts below fire only while that value is > 0.
- Alerts: `WalArchiveLagging` age > 600 s (warn); `RpoAtRisk` age > 840 s (page — one minute before the 04 I2 15-minute RPO); `WalArchiveFailing` = 2 failed `check` runs in a row (`lims_ops_wal_check_consecutive_failures >= 2`, page). There is no `RpoBreached` alert and no 1200 s threshold.
- Streaming standby on dr-1 normally holds data seconds behind (alert `StandbyLagHigh` > 60 s); the archive is the guarantee, the standby is the fast path.
- WAL volume (ASSUMPTION, measured in M2 and tracked by 06 R8): ≲ 50 writes/s at N = 10 (04 §14). Worst case with 60 s switching = 1,440 forced segments/day + 96 `check` switches = 1,536 segments × 16 MiB ≈ 24 GiB/day **before compression**; at repo2's 35-day retention that is ≈ 840 GiB, which together with base backups would not fit dr-1's 1 TB (§3.1). A force-switched segment carries little WAL in its 16 MiB; how small such segments become after `compress-type=zst` on this image is UNVERIFIED and is the M2 measurement. This is founder item **F-10** (08 A27.4: "DR site storage may need 2 TB; confirmed by the T-09 measurement before go-live"). If the measured archive exceeds 60 % of repo2's volume, R8's mitigation applies (larger dr-1 volume by B12, or a CR to raise `archive_timeout` — which would also need a new RPO decision); `DiskFillForecast` on dr-1 pages before it fills.

## 10. Logging and the audit store (04 D11; REQ-SEC-096/097/098)

### 10.1 Application/infra logs (DECISION: Fluent Bit → VictoriaLogs)
Options: Loki (AGPL), OpenSearch (JVM-heavy for 16 GB ops VM), VictoriaLogs (Apache-2.0, single binary). **Chosen VictoriaLogs 1.53.0** on ops-1 + **Fluent Bit 5.1.5** on every host.
- Inputs: Docker json-file logs (`/var/lib/docker/containers/*/*-json.log`, parser `docker`), journald (sshd, sudo, fail2ban, systemd timers), nginx `access.json`.
- Filters: `scrub.lua` — drops/redacts keys matching the CV §9.2 denylist (case-insensitive substrings: `name`, `phone`, `email`, `address`, `dob`, `birth`, `password`, `otp`, `token`, `jwt`, `cookie`, `secret`, `signature`, `barcode`, `registration_no`, `result`, `value`…) and regex scrubbers for phone-number and bearer-token patterns; adds `host`, `env`, `site`. This is defence in depth; the source rule is C0's logger.
- Output: HTTP JSON-lines ingestion of VictoriaLogs over wg0 (endpoint/params per the pinned VictoriaLogs docs, verified in T-17); buffering to disk on the host (`storage.type filesystem`, 1 GiB cap) so an ops-1 outage loses nothing for ~hours.
- Streams: `service`, `env`, `host`; `ops_audit` stream for operator actions.
- Retention: 90 days [CONV] (`-retentionPeriod=90d`); `ops_audit` copied nightly to the audit store (§10.3) for 5-year keeping.

### 10.2 What is never shipped
Raw HL7/ASTM messages (04 I8; stored by C7 in its archive), request bodies, query strings, PostgreSQL bind parameters (§7.7), Storage file names other than generated object paths (C0 random names), secrets.

### 10.3 Audit store (separate, append-only, ≥ 5 years)
- Separate PostgreSQL 17 instance (official `postgres:17` image by digest, C1 pins) on dr-1:5433, its own LUKS volume, own credentials; **different site and host** from the primary (04 D11 "shipped to a separate store"). After a DR promotion the primary also runs on dr-1, so this separation is lost for the degraded period; it is named in the incident record and ends with the switch-back (08 A25 D-210, `dr.md`, PRD AC-22.1).
- Ingestion: logical replication subscription `audit_ship` from publication `lims_audit_ship` (CR-C1-002) with `copy_data = false` (go-live start, no initial table copy), `streaming = on` [CONV]; insert-only publication so primary-side deletes never propagate. Whether a non-BYPASSRLS replication role can stream FORCE-RLS tables is **UNVERIFIED** → spike T-15 (logical decoding reads WAL and is not filtered by RLS; the initial-copy path is avoided by `copy_data = false`). Fallback if the spike fails: a pull job on dr-1 that reads new rows by `(occurred_at, id)` cursor through a C0-provided `SECURITY DEFINER` export function (new CR to C0-0B) — not designed further unless needed.
- Schema: `auditstore.audit_log`, `auditstore.access_log`, `auditstore.billing_activity_log` with **the same columns and types** as the source tables (generated by `gen-schema.sh` from a migrated staging DB with `pg_dump --schema-only --table=…`, then constraints other than PK and NOT NULL stripped, no FKs, no RLS). Subscriber tables live in schemas named like the publisher's (`audit`, `billing`) inside database `auditstore`, because logical replication matches schema-qualified names; `auditstore.*` names above are views for readers. See 05-SCHEMA §3 for DDL.
- Privileges: `audit_writer` (subscription owner) = INSERT only (+ what the apply worker needs; verified in T-15); `audit_reader` = SELECT on views, used only for investigations through an ops runbook with founder approval; no UPDATE/DELETE/TRUNCATE to anyone except the instance superuser, whose password is split (founder + ops lead) [CONV].
- Tamper evidence (REQ-SEC-097 "optional hash-chain per tenant"): nightly `digest.sql` computes per (tenant_id, day) `sha256` over rows ordered by `(occurred_at, id)` for each table and chains it with the previous day's digest into `auditstore_meta.daily_digests`; digests are also written to VictoriaLogs `ops_audit` and to the drill report — a later mismatch proves alteration.
- Retention: ≥ 5 years (04 D11; B15), config `audit_retention_years` default 5, validation refuses < 5; per-tenant longer values from C2's tenant setting are honoured by a purge job that is **not** enabled until B15 answers (nothing is deleted in the meantime).
- Schema drift: when C0 adds a column to a published table (additive migration) or relaxes a `NOT NULL`, the subscriber needs the change first, or the apply worker stops on the first row that uses it. Rule: `deploy.yml` runs `auditstore/gen-schema.sh --apply` on dr-1 **before** applying app migrations; `--apply` adds missing columns and drops a subscriber `NOT NULL` that the source no longer has (it never adds one) [CONV]; CI compares source and subscriber column **names, types and nullability** (job `auditstore-drift`). Current case (08 A29.2 / A28.5): `audit.audit_log.detail jsonb` (new) and nullable `actor_id` / `created_by` (maintenance-DEFINER rows) — mirrored in 05-SCHEMA §3.4.
- Lag metric `lims_ops_auditstore_lag_seconds` = now − max(occurred_at) of newest replicated row vs primary (sampled every minute), plus `pg_stat_subscription` and the publisher slot's `confirmed_flush_lsn` lag; alert > 300 s `AuditShippingLagging`, subscription disabled → `AuditShippingDown` (page).

3. Audit store schema sync (§10.3).
4. DB flow §7.9.
5. Rolling app update: api-a → health ready → api-b; worker-a (SIGTERM, 60 s grace) → worker-b; web; portal; renderer; pdf-sandbox.
6. `ci/smoke.sh`: synthetic journeys per chunk smoke suite (C0 nightly list) against the env; external tests (`tests/external/*`).
