# C17 Home Collection — 05 Schema (`homecollection` + device-local)

Status: DECISION draft, 2026-11-06. Part A is the specification C0-0B implements in `db/migrations/` and `db/policies/homecollection.sql` (CM §0). Conventions: 02-CV §5 (classes, mandatory columns, composite FKs per 04 D8, no ENUM, immutability trigger `app.enforce_mutable_columns`, RLS template, `lims_app` grants). Part B is the device-local drift schema owned and implemented by C17 itself (`apps/phlebo_app`).

PHI classes per column use 03-IC §1: **P0** none · **P1** pseudonymous ids · **P2** personal / lab-linked identifiers (name, phone, address, barcode, GPS of a home) · **P3** health data (orderables linked to a patient).

# Part A — server schema `homecollection`

## 1. Table inventory

| Table | Class (02-CV §5.2) | Scope | Purpose |
|---|---|---|---|
| `homecollection.settings` | M | tenant | one row per tenant (TRD §11.2), created lazily on first use (08 A17 P-22) |
| `homecollection.g_cs_reasons` | G | global | seeded reason codes, all sets — the only reason source in v1 (08 A19 D-130: no tenant overrides, no `cs_reasons` table) |
| `homecollection.booking_refs` | M (read model) | tenant | booking → visit, cancel-before-confirm guard |
| `homecollection.routes` | M | tenant + centre | one per (centre, phlebotomist, date); `version` = snapshot cursor input |
| `homecollection.visits` | C | tenant + centre | the visit (state machine 03-APP-FLOW §1.1) |

| `homecollection.mutations` | A | tenant + centre | every pushed mutation with its outcome |
| `homecollection.collections` | C | tenant + centre | collection facts; applied / held / discarded |
| `homecollection.handovers` | C | tenant + centre (from) + `to_centre_id` | custody hand-off |

| `homecollection.event_inbox` | A | tenant | consumer dedupe — **generated by C0** (C0 05-SCHEMA §3.9, `db/tools/gen-inbox.ts`); not specified here (review m#24) |

**Mandatory columns.** Every tenant table above has `id` + `UNIQUE (tenant_id, id)` (02-CV §5.2/§5.4), including `booking_refs` and `visit_specimens`, whose natural keys stay as `UNIQUE` constraints (review m#23). `g_cs_reasons` has `id` as PK and `(set_code, code)` as `UNIQUE`. There are no mandatory-column exceptions in this schema (08 A17 P-18(b)).

**Actor guard (08 A17 P-16).** `homecollection.*` is a staff module: no table is `shared_with` partner, portal or patient actors. Every `__tenant` policy carries `(SELECT app.is_staff_or_system())` in the transcribed predicate (`pred_t`, §4.1). The `__tenant_centre` policies need no extra term because `app.has_all_centres()` / `app.current_centre_ids()` are false/empty for partner, portal and patient actors (08 R3; same reasoning as C5 05-SCHEMA `pred_c`).

**Centre scoping decision (02-CV §5.8 "chunk decides").** Visits carry `centre_id` = the order's / booking's collection centre (normally the tenant's home-collection pseudo-centre, C0 `centre_kind = 'home_collection'`). Phlebotomists and dispatchers must hold that centre in their membership (or `all_centres`). Handovers and handover items are additionally visible through `to_centre_id`, so staff at the receiving centre can confirm them without being members of the home-collection centre. Receivers never need the centre-scoped visit tables (08 A19 D-125, data minimisation): H14 reads only `handovers` / `handover_items` (barcode and specimen type are copied onto `handover_items` when `handover.recorded` is applied), and H15 does not write `visit_flags` itself — it enqueues the worker task `homecollection.flag_handover_discrepancy`, which writes the `handover_discrepancy` flags as the module's system actor (all centres of the tenant).

**Cross-schema FKs (CM §5 R3).** `homecollection` (Wave 3) references `core`, `frontdesk` (patients, orders) and `lab` (specimens) — all upstream. No FK into `billing` (02-CV §5.4) and none into `engagement` (both Wave 3; no DAG order stated → booking ids are plain `uuid`).

**Published views.** 03-IC §6 defines none for `homecollection`; this chunk publishes none.

### 4.2 Retention anonymisation DEFINER (08 A19 P-41; A10.5, A12.2, A12.7)

`homecollection.purge_retention` (TRD §10, `tenantScope: 'per_tenant'`, 08 A13 P-6) runs once per tenant under that tenant's system-actor claims and calls the function below with `p_before = now() − retentionYears` (C2 `IdentityPort.getTenantSettings(['retentionYears'])`). The function anonymises the P2 free-text and location columns of closed visits and the copied barcodes on their handover items (08 A19 D-125: "they follow the visits' retention and anonymisation"); rows are kept (class C). It is the only SECURITY DEFINER requested by C17. The `visit_locations` retention delete is **not** a DEFINER (§4.1 (3)).

Barcode placeholder: `handover_items.barcode` stays `NOT NULL` with its pattern (D-125), so anonymisation overwrites it with the literal `'ANONYMISED'` [CONV: matches `^[A-Z0-9]{1,20}$`; only written to items of closed visits past retention, which no handover flow reads any more].

```sql
-- Owner policies (TO lims_owner, narrowest USING; 08 A10.5). Gate: app.maintenance set inside the body (A12.2)
-- AND the tenant of the per-tenant job's claims (one tenant per call, same pattern as C7 05-SCHEMA (c)).
CREATE POLICY visits__select__owner_only ON homecollection.visits FOR SELECT TO lims_owner
  USING (current_setting('app.maintenance', true) = 'homecollection_anonymise_retired_visits'
         AND tenant_id = (SELECT app.current_tenant_id())
         AND status IN ('completed','failed','cancelled'));
CREATE POLICY visits__update__owner_only ON homecollection.visits FOR UPDATE TO lims_owner
  USING (current_setting('app.maintenance', true) = 'homecollection_anonymise_retired_visits'
         AND tenant_id = (SELECT app.current_tenant_id())
         AND status IN ('completed','failed','cancelled'))
  WITH CHECK (current_setting('app.maintenance', true) = 'homecollection_anonymise_retired_visits'
         AND tenant_id = (SELECT app.current_tenant_id())
         AND status IN ('completed','failed','cancelled'));
CREATE POLICY handover_items__select__owner_only ON homecollection.handover_items FOR SELECT TO lims_owner
  USING (current_setting('app.maintenance', true) = 'homecollection_anonymise_retired_visits'
         AND tenant_id = (SELECT app.current_tenant_id()));
CREATE POLICY handover_items__update__owner_only ON homecollection.handover_items FOR UPDATE TO lims_owner
  USING (current_setting('app.maintenance', true) = 'homecollection_anonymise_retired_visits'
         AND tenant_id = (SELECT app.current_tenant_id()))
  WITH CHECK (current_setting('app.maintenance', true) = 'homecollection_anonymise_retired_visits'
         AND tenant_id = (SELECT app.current_tenant_id())
         AND barcode = 'ANONYMISED');

CREATE FUNCTION app.homecollection_anonymise_retired_visits(p_before timestamptz)
RETURNS TABLE (visits_anonymised integer, handover_items_anonymised integer)
LANGUAGE plpgsql VOLATILE SECURITY DEFINER SET search_path = '' AS $$
DECLARE
  v_tenant uuid := app.current_tenant_id();
  v_actor  uuid := app.current_actor_id();
  v_visits integer;
  v_items  integer;
BEGIN
  IF v_tenant IS NULL OR v_actor IS NULL OR app.current_actor_type() IS DISTINCT FROM 'system'
     OR p_before IS NULL OR p_before > now() THEN
    RAISE EXCEPTION USING ERRCODE = 'P0001', MESSAGE = 'homecollection_anonymise_invalid_input';
  END IF;
  PERFORM set_config('app.maintenance', 'homecollection_anonymise_retired_visits', true);
  UPDATE homecollection.visits v
     SET address_text = NULL, landmark = NULL, latitude = NULL, longitude = NULL,
         note_for_phlebotomist = NULL, status_reason_text = NULL,
         updated_at = now(), updated_by = v_actor, version = v.version + 1
   WHERE v.tenant_id = v_tenant
     AND v.status IN ('completed','failed','cancelled')
     AND coalesce(v.completed_at, v.failed_at, v.cancelled_at, v.updated_at) < p_before
     AND (v.address_text IS NOT NULL OR v.landmark IS NOT NULL OR v.latitude IS NOT NULL
          OR v.note_for_phlebotomist IS NOT NULL OR v.status_reason_text IS NOT NULL);
  GET DIAGNOSTICS v_visits = ROW_COUNT;
  UPDATE homecollection.handover_items hi
     SET barcode = 'ANONYMISED', updated_at = now(), updated_by = v_actor, version = hi.version + 1
   WHERE hi.tenant_id = v_tenant
     AND hi.barcode <> 'ANONYMISED'
     AND EXISTS (SELECT 1 FROM homecollection.visits v
                  WHERE v.tenant_id = hi.tenant_id AND v.id = hi.visit_id
                    AND v.status IN ('completed','failed','cancelled')
                    AND coalesce(v.completed_at, v.failed_at, v.cancelled_at, v.updated_at) < p_before);
  GET DIAGNOSTICS v_items = ROW_COUNT;
  PERFORM set_config('app.maintenance', '', true);
  RETURN QUERY SELECT v_visits, v_items;
END $$;
REVOKE ALL ON FUNCTION app.homecollection_anonymise_retired_visits(timestamptz) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION app.homecollection_anonymise_retired_visits(timestamptz) TO lims_worker;
```

Notes: the second UPDATE's `EXISTS` reads `visits` through `visits__select__owner_only` (same gate). The `visits__mutable_columns` trigger already lists every column written here; the C0 transition guard allows it only under the condition in §4 (`current_user = 'lims_owner'` and the maintenance value). `handover_items__mutable_columns` is skipped by its `WHEN` clause under the same condition. Already anonymised rows are not touched again (idempotent monthly run). `visit_flags.resolution_note`, `collections.review_reason_text`, `handovers.note`, `visit_transitions.reason_text` and `mutations.payload` are outside this function, as before this fix pass (unchanged scope; A-class rows are never updated).

```sql
  body_json TEXT NOT NULL,                                      -- serialized PushRequest, written once, re-sent byte for byte
  created_at TEXT NOT NULL
);

CREATE TABLE clock_anchors (
  anchor_id TEXT PRIMARY KEY NOT NULL,          -- UUIDv7
  server_time TEXT NOT NULL,                    -- IsoUtc from response body
  device_wall_time TEXT NOT NULL,
  monotonic_ms INTEGER NOT NULL,
  boot_id TEXT NOT NULL,
  created_seq INTEGER NOT NULL                  -- device_seq value at creation (anchors kept while referenced)
);

CREATE TABLE mutation_log (
  client_mutation_id TEXT PRIMARY KEY NOT NULL,                 -- UUIDv7 (lims_shared)
  device_seq INTEGER NOT NULL UNIQUE,                           -- strictly increasing, from device_state.next_device_seq
  type TEXT NOT NULL CHECK (type IN ('visit.arrived','visit.identity_checked','visit.consent_recorded','specimen.collected',
        'specimen.not_collected','payment.captured','visit.completed','visit.failed','handover.recorded')),
  visit_id TEXT,                                                -- NULL only for handover.recorded
  visit_label TEXT,                                             -- "#3 · 07:15–07:45" — no PHI, for the Outbox screen
  payload_json TEXT NOT NULL,                                   -- immutable after insert (canonical JSON, sorted keys)
  payload_sha256 TEXT NOT NULL,                                 -- of payload_json bytes; LOCAL ONLY (device integrity check), never sent;
                                                                --   the server computes its own payload_sha256 over JCS (RFC 8785) of payload (review m#38)
  captured_wall_time TEXT NOT NULL,
  anchor_id TEXT NOT NULL REFERENCES clock_anchors(anchor_id),
  elapsed_since_anchor_ms INTEGER NOT NULL,
  state TEXT NOT NULL CHECK (state IN ('pending','sending','applied','duplicate','held','rejected')) DEFAULT 'pending',
  outcome_code TEXT,
  batch_id TEXT REFERENCES batches(batch_id),                   -- set when first included in a batch; reused on retry
  attempts INTEGER NOT NULL DEFAULT 0,
  last_attempt_at TEXT,
  terminal_at TEXT                                              -- when state became applied|duplicate|held|rejected
);
CREATE INDEX mutation_log_state_seq ON mutation_log(state, device_seq);
CREATE INDEX mutation_log_visit ON mutation_log(visit_id, device_seq);
```
Invariants (unit-tested):
1. `payload_json`, `type`, `visit_id`, `device_seq`, capture fields are never updated; only `state`, `outcome_code`, `batch_id`, `attempts`, `last_attempt_at`, `terminal_at` change.
2. A row is written in the same SQLite transaction that increments `next_device_seq`; the UI shows "Saved on phone" only after commit.
3. Batching (review #3): oldest `pending` rows by `device_seq`, ≤ 100 and ≤ 512 KB serialized. Forming a batch writes one `batches` row with the complete serialized `PushRequest` (`sent_at_device`, `anchors`, `now.*` and the mutations, fixed at that moment) and moves the rows to `sending` with that `batch_id`, in one SQLite transaction. Every retry (timeout, network error, 5xx, `401 auth.token_expired` after refresh, `409 common.idempotency_in_progress`) re-sends `body_json` **byte for byte** with the same Idempotency-Key, so the core request hash never changes. A new batch is formed only after a response for the old one. On `422 common.idempotency_key_reused` for a push (body and key no longer match the stored request, e.g. after an app reinstall restored an old key), the device deletes the `batches` row, gives the rows a new `batch_id` and forms a new body; per-mutation dedupe on `client_mutation_id` makes this safe (TRD §7.2). The `batches` row is deleted when its rows are terminal.
4. Terminal rows are deleted 24 h after `terminal_at` [CONV]; anchors not referenced by any row and older than the newest anchor are deleted.
5. Logout permitted only when `SELECT count(*) FROM mutation_log WHERE state IN ('pending','sending') = 0` **and** the server sign-off (A5) succeeds.

Payload JSON per type = the `payload` objects in TRD §6.3 (snake_case). No patient name, phone, address or test name may appear in any payload (unit test scans payload keys against a denylist).

## B.3 Secure-storage keys (`flutter_secure_storage`)

| Key | Value | Removed |
|---|---|---|
| `phlebo.device_id` | UUIDv7, generated **before the first login** (it is the C2 `app_instance_id`, review #8); **regenerated after sign-off or wipe** | sign-off, wipe |
| `phlebo.outbox_owner_user_id` | the C2 user id (`sub`) of the first successful login on this outbox (review #12) | sign-off, wipe (with the outbox) |
| `phlebo.cache_db_key` | 32 random bytes hex | every cache destruction (new key per new cache) |
| `phlebo.outbox_db_key` | 32 random bytes hex | sign-off, wipe |
| `phlebo.session_token`, `phlebo.access_expires_at`, `phlebo.session_expires_at` | C2 mobile session (kind `staff_mobile`; opaque rotating LIMS session token, never a GoTrue refresh token — 08 R10) | logout, revoke, wipe |

Device-id regeneration (DECISION) means a server `devices` row ends at `signed_off` or `wiped` (terminal, 03-APP-FLOW §1.4); a new login on the same phone registers a new device row, so a device id never moves between memberships or tenants.

Outbox owner binding (review #12): while `outbox.db` has rows in a non-terminal state, the app accepts a login only when the returned user id equals `phlebo.outbox_owner_user_id`; another user gets "This phone has unsent changes from another user. Ask that user to sign in, or the lab admin to wipe it." and the new session is closed (`logoutMobileSession`). With no non-terminal rows the old binding no longer matters: if A1 then answers `409 homecollection.device_not_registered` (the device id is still bound to the previous membership, e.g. after a revoke without sign-off), the app closes the new session, destroys `outbox.db` and its key, generates a new device id and shows the login screen again with "Sign in again to set up this phone." [DECISION: the device id is the C2 `app_instance_id`, so it must be fixed before the login request].
