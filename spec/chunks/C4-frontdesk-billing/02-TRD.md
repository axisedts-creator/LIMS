Every cron entry in both manifests declares `tenantScope: 'per_tenant'` (08 A13 P-6: the worker core enqueues one job per tenant with `core.tenants.status IN ('active','suspended')`, payload `{tenant_id}`, `job_key = '<identifier>:<tenant_id>:<tick ISO minute>'`, run under that tenant's claims for the module system actor); none is `platform`.

Branding assets for invoice/register PDFs need no extra permission: `IdentityPort.readBrandingAsset` accepts any `user` or `system` actor of the tenant (08 A13 D-26).

## 4. Internal boundary between `frontdesk` and `billing`

```
            ┌──────────── frontdesk ────────────┐          ┌──────────── billing ─────────────┐
 HTTP ───▶  registration.service               │  ports   │ BillingCommandPort.impl          │
            │  CatalogPort (C3) → prices        │ ───────▶ │   computeQuote / issueOrderInvoice│
            │  BillingCommandPort.computeQuote  │  same tx │   recordPayment / creditCharges   │
            │  … writes frontdesk.* rows        │          │   raiseCreditNoteRequirement      │
            │  BillingCommandPort.issue…        │          │ BillingPort.impl (C6,C13,C15..)   │
            └───────────────────────────────────┘ ◀─────── │   uses FrontdeskPort.getOrderSummary
                                                 FrontdeskPort (billing needs billing_mode,
                                                 centre, credit party of an order)
```
Rules:
1. `frontdesk` never reads `billing.*` tables and vice versa (02-CV §5.13 CI grep). All cross-module calls go through `ctx.ports.BillingCommandPort`, `ctx.ports.BillingPort` or `ctx.ports.FrontdeskPort`, inside the caller's `ctx.tx` (02-CV §8.1), so a registration is **one** atomic transaction across both schemas.
2. Billing keeps its own snapshot of everything a fiscal document needs (buyer name, lines, referrer id, department id): a billing record never depends on a later frontdesk change.
3. No FK from `billing` to `frontdesk` (DECISION, stricter than 02-CV §5.4 allows): `order_id`, `order_item_id`, `patient_id` in billing are plain `uuid` validated by the port caller in the same transaction. Rationale: keeps `billing` movable to its own schema/DB (04 D16, B17) without rewriting FKs.
4. Until Agent BL merges, Agent FD runs against the `BillingCommandPort` fake (C0, `packages/fakes`); until FD merges, BL's contract tests seed orders through the `FrontdeskPort` fake.

## 5. Endpoints

Conventions for every row: `security: bearerJwt` (via BFF), `x-rate-limit-tier: general` (10 req/s/user, burst 20 — 04 §4), problem+json errors (02-CV §4.6) and the common codes `common.validation_failed`, `common.not_found`, `auth.forbidden`, `auth.unauthenticated`, `common.rate_limited`, `common.internal` are implied in `x-error-codes`. "Idem" = `x-idempotency`. Mutating actions on versioned resources require `If-Match` (02-CV §4.2) where marked "IM". Field types: `uuid` = Uuidv7 string; `money` = `{amount_paisa, currency:"NPR"}` (02-CV §4.9); `instant` = IsoUtc. All objects `additionalProperties: false`; strings have `maxLength` (values in brackets).

### 6.2 Implemented: `BillingPort` (03-IC §4.4 + 08 §4.14 additions)
```ts
getReleaseEligibility(ctx, { orderId }): Promise<ReleaseEligibility>;
recordGatewayPayment(ctx, input: GatewayPaymentInput): Promise<{ ledgerEntryId; duplicate; balance: OrderBalance }>;   // GatewayPaymentInput += allowExceedsDue?

```
**Callers are staff (`user`) or `system` actors only** (08 R8): C15 calls it in its verifying job/callback context (system) or in a staff request; C6 and C13 read eligibility/balance as staff or system. Patient and portal contexts never call BillingPort — the impl checks `ctx.actor.type ∈ {user, system}` first and otherwise throws `auth.forbidden`.
Eligibility algorithm (first match wins):
1. `IdentityPort.getTenantSettings(['releaseRequiresPayment'])` false → `eligible, policy_not_enforced`.
2. Order `billing_mode = credit` (via `FrontdeskPort.getOrderSummary`) → `eligible, credit_party`.
3. An active `billing.release_overrides` row (not expired) → `eligible, override, overrideId`.
4. No issued invoice for the order and no credit charges → `not eligible, no_invoice`.
5. `balance_due ≤ 0` and `paid > 0` → `eligible, paid_in_full`; `balance_due ≤ 0` and `paid = 0` → `eligible, zero_balance`.
6. otherwise → `not eligible, due_outstanding`.
`balanceDue` always returned; `evaluatedAt = ctx.now()`. p95 ≤ 15 ms (one indexed read of `order_balances` + overrides).

`recordGatewayPayment`: (a) existing row for unique `(tenant_id, gateway, gateway_txn_ref)` → return it, `duplicate: true`; (b) if `billing.payment_intent_refs` holds the intent (created via B12) and `amount ≠ stored amount` → `billing.amount_mismatch`; intents created elsewhere (C16) have no ref row → C15's own exact-amount check (04 P7) is authoritative; (c) `amount > balance_due` → `billing.payment_exceeds_due` (contract case 8) unless `allowExceedsDue = true`, in which case the full amount is recorded and a `billing.finance_review_items` row `kind = 'gateway_payment_exceeds_due'` is inserted in the same transaction; (d) insert ledger row `capture_kind = gateway`, `method_code = <gateway>`, `collected_by_membership_id = NULL` (gateway capture has no collector — CHECK in 05-SCHEMA, 08 R8); recompute balance (version + 1), emit `billing.balance.changed.v1` (`cause: gateway_payment_recorded`). p95 ≤ 50 ms.

`recordGatewayRefund` (gateway refunds keep C15's own two-person approval, C15 P8/P9; no `billing.refund_requests` row): (a) existing row with `idempotency_key = 'gw_refund:'+refundId` → return it, `duplicate: true`; (b) `amount` > refundable (gateway payments of the intent − earlier gateway refunds) → `billing.ledger_reversal_invalid`; (c) insert ledger row `entry_kind = refund`, `capture_kind = gateway`, `amount_paisa = −amount`, `reason_code`, `approved_by_membership_id`, `collected_by_membership_id = NULL`; recompute balance, emit `billing.balance.changed.v1` (`cause: payment_reversed`). Contract cases added by 08: (11) refund idempotent; (12) refund > refundable → `billing.ledger_reversal_invalid`; (13) `allowExceedsDue` records + review item; (14) patient/portal actor → `auth.forbidden`.

Balance: `invoiced = Σ net of issued invoices of the order (any status)`, `credited = Σ credit notes against those invoices`, `paid = Σ signed ledger amounts (payments positive, reversals/refunds negative)`, `balance_due = invoiced − credited − paid`. Stored in `billing.order_balances` with `balance_version` (strictly increasing; incremented only when one of the four amounts changes).

## 12. Gapless numbering — locking design (04 L7, REQ-ARCH-031/032)

```
counter.service.allocate(tx, {series, fiscalYearBs})            -- called LAST before inserting the document
  0. pattern check: series 'INV:<branch_code>' (scope = branch) and invoiceNoPattern without {branch}
       → billing.numbering_pattern_invalid (409; 08 A13 D-23) — nothing allocated
  1. SELECT set_config('lock_timeout', '<LIMS_BILLING_COUNTER_LOCK_TIMEOUT_MS>ms', true);
  2. UPDATE billing.fiscal_counters
        SET last_no = last_no + 1, updated_at = now(), updated_by = $actor
      WHERE tenant_id = $tenant AND series = $series AND fiscal_year_bs = $fy AND closed_at IS NULL
      RETURNING last_no, clock_timestamp() AS allocated_at;
     -- 0 rows: if the row is missing → INSERT … (last_no 0) ON CONFLICT DO NOTHING, then retry UPDATE once;
     --          if closed → billing.fiscal_year_closed
     -- SQLSTATE 55P03 (lock_not_available) raised by THIS statement → billing.counter_busy (503, Retry-After: 1)
  2a. SELECT set_config('lock_timeout', '0', true);   -- reset at once, so a later 55P03 elsewhere is not mis-mapped (review C4 #29)
  3. fyCheck = fiscalYearOf(allocated_at, tenant tz); if fyCheck ≠ $fy → throw billing.counter_busy with
     detail "fiscal_year_rollover" (08 A13 D-25); the caller's transaction rolls back (counter UPDATE included → no gap)
  4. issued_at := allocated_at; invoice_no := format(pattern, fy, last_no)
  5. INSERT invoice (invoice_seq = last_no, issued_at) + lines + outbox; COMMIT
```
- **Retry across the port (08 A13 D-25):** billing never retries a transaction it does not own. `frontdesk` registration (F9), confirmation (F12) and item change (F13) — and the booking consumer / `createOrderFromBooking` paths — retry their **whole** transaction once on `billing.counter_busy` (any detail) and on SQLSTATE `40P01` (deadlock); a second failure is returned (`503 billing.counter_busy`). Billing-owned flows (B4, B5, B8, B10a, B21, B22) apply the same single retry in their own service.
- Series keys: `INV` (or `INV:<branch_code>` when `invoice_series_scope = branch`), `CN`, `RC` (03-IC §9.3).
- Gapless: the counter row update and the document insert commit or roll back together; no Postgres `SEQUENCE` is used anywhere in `billing` (CI check).
- Chronological: `issued_at` is taken from `clock_timestamp()` **after** the row lock is held, so for a series `issued_at` is monotonic in `invoice_seq`; a DB trigger (05-SCHEMA §4) rejects an insert whose `(invoice_seq, issued_at)` is not greater than the series maximum, and rejects `NEW.last_no ≠ OLD.last_no + 1` on counters.
- Lock window (statements between step 2 and COMMIT; review C4 #28): one invoice insert, ≤ 200 line inserts (multi-row), the `order_balances` upsert, ≤ 5 ledger inserts (registration payments; receipt numbers are not allocated in the registration transaction), the `sendSms` outbox insert (NotificationPort writes a delivery row + enqueue in `ctx.tx`), ≤ (3 + number of payments) `events.publish` (`invoice.issued`, one `balance.changed` per balance change = 1 + payments, `order.created`), ≤ 1 `app.enqueue_job` (CBMS) → target ≤ 50 ms p95. Catalog calls, the quote, patient/order/discount writes and discount checks run **before** step 2.
- Lock order within one transaction (deadlock avoidance): per order, the `order_balances` row is locked (`FOR UPDATE`) before any `RC` counter; an `INV`/`CN` counter is always taken last, immediately before its document insert; B4 locks the invoice row, then `order_balances`, then the `CN` counter. Remaining deadlocks (40P01) are retried once (above).
- Contention arithmetic (04 §14): 125 registrations/h/lab at peak → one allocation per ~29 s per tenant series; utilisation = 0.05 s / 28.8 s ≈ 0.17 %. Burst of 20 centres submitting simultaneously → worst wait ≈ 20 × 50 ms = 1 s < 3 s lock timeout.
- FY derivation: `fiscalYearOf` converts the instant to the tenant time zone date, then to B.S. via `bsdate`; FY = `y/(y+1)` if B.S. month ≥ 4 (Shrawan) else `(y−1)/y`. Golden cases include the 01 §4.8 fact "FY 2082/83 commenced 1 Shrawan = 17 Jul 2025" (2025-07-16 23:59 NPT → 2081/82; 2025-07-17 00:00 NPT → 2082/83).

## 13. Isolatability (04 D16, B17) — per-tenant export/restore
